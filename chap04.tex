\chapter{Architecture}

This chapter describes the architecture of our app.
The main project is stored in \texttt{refdocgen/src/RefDocGen} folder and further divided into the following folders:

\begin{itemize}
    \item \texttt{AssemblyAnalysis} -- contains types responsible for extracting the relevant data from an assembly.
    \item \texttt{CodeElements} -- contains objects representing the types and members, introduced in sections~\ref{sec:member-repr} and \ref{sec:type-repr}.
    \item \texttt{Config} -- contains all types related to program configuration.
    \item \texttt{DocExtraction} -- contains types responsible for extracting the documentation from the XML file and assigning it to the corresponding types or members.
    \item \texttt{TemplateProcessors} -- contains types responsible for generating the reference documentation from the type and member objects.
    This folder also includes \textit{Razor} templates, representing individual fragments of the UI.
\end{itemize}

Additionally, the project also contains a \texttt{Tools} folder, containing additional tools shared between multiple parts of the project.

\section{Workflow}
\label{sec:workflow}

The simplified process of generating documentation is displayed in Figure~\ref{fig:workflow}.
First, it is necessary to extract the information from an assembly and create the objects representing types and members, which is performed by the \texttt{AssemblyTypeExtractor} class.
These objects are then stored within the \texttt{TypeRegistry} class, which is further passed to the \texttt{DocCommentExtractor}.
This class extracts the documentation comments from the XML documentation file and assigns them to the corresponding types and members.
Hence, the \texttt{TypeRegistry} now contains documentation as well.
Next, the registry is passed to the \texttt{ITemplateProcessor} interface, which represents the base interface for processing various types of templates, as described in section~\ref{sec:template-extensibility}.
The default implementation, called \texttt{RazorTemplateProcessor}, uses \textit{Razor} templates, processes them with the provided data, and thus creates the reference documentation.

The entire process is coordinated by the \texttt{DocGenerator.GenerateDoc} method, which gets called directly from the \texttt{Program} class.
In the following sections, we will describe the individual parts of the codebase in more detail.

\section{Type registry}

\label{sec:type-registry}

As mentioned in the previous section, the collection of declared types and members is stored within a \texttt{TypeRegistry} instance and shared between various parts of the application.
More specifically, the \texttt{TypeRegistry} is used in two places.
First, it is accessed by the \texttt{DocCommentExtractor} and related classes to assign XML documentation comments to the appropriate types and members.
After that, the data from the \texttt{TypeRegistry} is used by the template processors (such as the default \texttt{RazorTemplateProcessor}), and based on this data, the resulting documentation is generated.

For now, we will consider only the usage by the \texttt{DocCommentExtractor} and return to the second case later.
Internally, the \texttt{TypeRegistry} organizes the types into the following three categories: enums, delegates, and the remaining types (classes, structures, and interfaces), which we will refer to as the \textit{object types}.
Each of these categories of types is stored in a dictionary, indexed by the ID string, which is equal to the ID string used in the XML documentation file. 
The format of the string is further described in Section~\ref{sec:id-string} and the official .NET documentation~\cite{csharp_xml_docs}.

\subsection{Types}

As mentioned in the previous section, the type registry stores all the declared types organized into three categories.
Next, it is crucial to note that we use custom objects to represent types, which was explained in the section~\ref{sec:type-repr}, 
Unlike \texttt{System.Type}, there are multiple classes representing different kinds of types, which fundamentally differ in structure:

\begin{itemize}
    \item \texttt{EnumTypeData} -- represents an enum.
    \item \texttt{DelegateTypeData} -- represents a delegate.
    \item \texttt{ObjectTypeData} -- represents an object type (i.e., a class, structure, or an interface).
\end{itemize}

These objects contain all relevant data about a type, such as its name, namespace, etc., as well as its documentation comments and a collection of declared members.
As illustrated in Figure~\ref{fig:types-concrete}, all these classes inherit from the \texttt{TypeDeclaration} class, which contains the common code.
The documentation comments are stored in separate properties as \texttt{XElement} instances; 
hence the classes have properties called \texttt{SummaryDocComment}, \texttt{RemarksDocComment}, etc.
Importantly, these properties are writable, unlike the rest of the data.
This is necessary because the documentation comments are assigned after the members are created, as explained earlier.

Additionally, the \texttt{ObjectTypeData} stores its members in dictionaries, indexed by the member IDs, similar to how the types are stored in the \texttt{TypeRegistry}.
The member ID corresponds to its identifier in the XML documentation file; the only difference is that, in our case, the type name is not part of the ID.
The members are stored according to their kind; therefore, the \texttt{ObjectTypeData} class declares seven distinct dictionaries, containing fields, properties, indexers, methods, operators, constructors, and events.
This is illustrated in Figure~\ref{fig:objecttype-structure}, which shows a simplified internal structure of an \texttt{ObjectTypeData} instance, containing relevant data of its two fields, \texttt{name} and \texttt{age}, and two properties, named \texttt{IsAdult} and \texttt{IsAdmin}.

\caption{\texttt{ObjectTypeData} instance -- simplified structure}
\label{fig:objecttype-structure}

Accordingly, the \texttt{EnumData} class contains a dictionary of enum members.
Moreover, if a type defines any type parameters, these are also stored in a separate dictionary indexed by their names, while the individual type parameters are represented by a custom class named \texttt{TypeParameterData}.
Additionally, the program uses the \texttt{AttributeData} class to represent user-defined attributes.

Furthermore, it is important to recognize that we also need to represent, e.g., a type of field or the return type of a method, in our codebase.
In such cases, we only need the name-related information of a type; in particular, we do not need any documentation comments, nor a collection of its members.
For such purposes, the \texttt{TypeNameData} class is used.
The functionality shared between \texttt{TypeNameData} and \texttt{TypeDeclaration} is extracted to the \texttt{TypeNameBaseData} class.

\subsection{Members}

Similarly to types, the members are represented by custom objects, as outlined in Section~\ref{sec:member-repr}.
There is a separate class for each kind of member, such as field, method, and property, as illustrated in Figure~\ref{fig:members-concrete}.
Essentially, these objects wrap the types provided by reflection (such as \texttt{FieldInfo} and \texttt{MethodInfo}) and provide all the necessary information about the member, as well as its documentation comments.
Hence, for instance, the \texttt{FieldData} class wraps a \texttt{FieldInfo} instance.
Additionally, there is a separate class for operators (\texttt{OperatorData}) and indexers (\texttt{IndexerData}), inherited from \texttt{MethodData}, or \texttt{PropertyData}, respectively.
That is because an overloaded operator in .NET is essentially a method using a special syntax, and similarly, an indexer is a special case of a .NET property.

All member classes inherit from a base class, called \texttt{MemberData}, which declares the common properties, such as the summary and remarks documentation comments, member name, etc.
Similarly, the \texttt{MethodLikeMemberData} class encapsulates the functionality shared between methods and constructors.
Additionally, methods, operators, constructors, and indexers may have parameters, which are represented by the \texttt{ParameterData} class.
Similarly to type parameters, the parameters are also stored within a dictionary, indexed by their names.

\subsection{Type and member interfaces}

As mentioned earlier, the other part of our codebase using the \texttt{TypeRegistry} is the template processors, e.g., the default \texttt{RazorTemplateProcessor}.
Here, the goal is to generate the resulting documentation based on the data.

We should strive to make the API as user-friendly as possible, especially because it may be used by other developers who develop custom template processors.
Thus, we decided to use the \texttt{ITypeRegistry} interface, which is implemented by the \texttt{TypeRegistry} class, and exposes the registry data as read-only.
Furthermore, unlike the \texttt{TypeRegistry} class, the object types, delegates, and enums are not returned as dictionaries, but within an enumerable instead.
Accordingly, the members within a type are also returned as an enumerable.
 
Moreover, when using the \texttt{ITypeRegistry} interface, the types are not returned as \texttt{ObjectTypeData}, \texttt{EnumTypeData}, and \texttt{DelegateTypeData} instances; instead, a corresponding interface, offering a read-only view of the data, is returned. 
Hence, there is a corresponding interface for each of the type classes; for example, the \texttt{IObjectTypeData} interface is implemented by the \texttt{ObjectTypeData} class.
The inheritance structure of these interfaces is displayed in Figure~\ref{fig:types-abstract}.

Accordingly, the members within a type are also returned as interfaces, which allow us only to read the data.
As with types, there is a separate interface for each of the member classes; for example, the \texttt{FieldData} class implements the \texttt{IFieldData} interface.
In addition, several super-interfaces represent common properties of a selection of members, as shown in Figure~\ref{fig:member-interfaces}.
Using the \texttt{IParametrizedMemberData} interface, which represents a member that may have parameters (i.e., a constructor, method, or indexer), it is possible to handle those types in the same way.
The same goes for handling members storing a value, represented by \texttt{IValueMemberData} interface, or for \texttt{ICallableMemberData} providing the shared data of properties, methods, and events.

\section{Extracting the data from an assembly}
\label{sec:architecture-assembly-analysis}

In the previous section, we described the internal structure of the \texttt{TypeRegistry}, and
now, we need to explain how the data from the assembly is loaded and the registry is created.
As mentioned earlier, this task is managed by the \texttt{AssemblyTypeExtractor} class, which uses reflection to load the assembly and obtain the declared types.
Individual assemblies are loaded using the \texttt{Assembly\-DependencyLoadContext} class.

It is also important to mention that besides creating the type registry, the \texttt{AssemblyTypeExtractor} class is also responsible for filtering the types that will be included in the documentation.
Thus, if the user chooses to exclude types contained in a given assembly or namespace, as described in Requirements~\ref{req:exclude-assemblies} and~\ref{req:exclude-namespaces}, these types are simply ignored.
The same applies to excluding members with given accessibility, or the inherited ones, as requested in Requirements~\ref{req:exclude-accessibility} and~\ref{req:exclude-inherited}.
The configuration containing this information is provided to the \texttt{AssemblyTypeExtractor} as an \texttt{AssemblyDataConfiguration} instance.

Next, the \texttt{AssemblyTypeExtractor} class converts the loaded types, represented as \texttt{System.Type} instances, to the corresponding \texttt{ObjectTypeData}, \texttt{Enum\-TypeData}, and \texttt{DelegateTypeData} objects.
Since the initialization of the \texttt{Object\-TypeData} instance is quite complex, as it contains a large number of properties, we applied the builder pattern using the \texttt{ObjectTypeDataBuilder} class.

Moreover, each member object is created from its corresponding reflection type.
For instance, a \texttt{FieldData} object is constructed from the corresponding \texttt{FieldInfo} instance provided by reflection, along with additional data (such as the reference to the declaring type), as displayed in Figure~\ref{fig:assembly-creators}.
This task is performed by dedicated creator classes, with a separate class for each category of members.
These classes are named \texttt{FieldDataCreator}, \texttt{MethodDataCreator}, etc., and called from within the \texttt{ObjectTypeDataBuilder}. 
Additionally, many of those creator classes use the \texttt{MemberCreatorHelper} class, which contains shared functionality, such as the creation of \texttt{ParameterData} instances from the corresponding \texttt{ParameterInfo} objects.

For constructing other type classes (namely \texttt{EnumTypeData} and \texttt{DelegateType\-Data}), no builder pattern is used, as these objects are significantly less complex.
Instead, this task is performed directly by the corresponding methods of the \texttt{AssemblyTypeExtractor} class.
After all the custom type objects are created, a \texttt{TypeRegistry} instance is initialized with this data and returned.

\section{Adding the documentation}

Now that we understand the internal structure of the \texttt{TypeRegistry} instance and how it is created, the next step is to add the documentation comments.
The whole process is managed by the \texttt{DocCommentExtractor} class, which loads the XML documentation file and processes the XML comments one by one.
As mentioned in Section~\ref{sec:workflow}, this class accesses the \texttt{TypeRegistry} instance and adds the documentation to the corresponding types and members.
Additionally, all \texttt{<inheritdoc>} tags are resolved and replaced with the actual documentation.

\subsection{Assignment of the documentation comments}

Each comment is identified by an ID that determines the corresponding type or member, as previously explained in Section~\ref{sec:type-registry}.
Hence, the \texttt{DocCommentExtractor} class first parses the ID and checks whether the documentation belongs to a type or a member.
If it belongs to a type, the corresponding \texttt{TypeDeclaration} instance is obtained from the \texttt{TypeRegistry} based on the ID.
Then, the instance together with the raw XML documentation is passed to the \texttt{TypeDocHandler} class, which parses the XML and assigns the individual documentation comments (summary, remarks, etc.) to the given type.
Similarly, if the type is a delegate, the \texttt{DelegateDocHandler} class is used. 
This class inherits from the \texttt{TypeDocHandler} and thus performs the same operations.
In addition to that, it also assigns the documentation comments specific to delegates, such as those for parameters and return values.

If the documentation belongs to a member, the \texttt{DocCommentExtractor} again first obtains the type containing the member from the registry.
Next, one of the member documentation handlers is called.
There is a corresponding documentation handler for each member, as illustrated in Figure~\ref{fig:documentation-handlers}.
All member handlers accept the following three parameters: the containing type, the member ID, and the raw XML documentation.
Then, the handler parses the raw XML and assigns the contained documentation comments, similarly to the \texttt{TypeDocHandler}.

All handlers inherit from the base class, called \texttt{MemberDocHandler}, which is responsible for assigning the \texttt{<summary>}, \texttt{<remarks>}, \texttt{<example>}, and \texttt{<seealso>} documentation tags, as these are valid for any member.
The individual handlers then assign only the remaining comments, which differ for each member kind.
Furthermore, the shared functionality related to method-like members is extracted to the \texttt{MethodLikeMemberDocHandler} class.

\subsection{Resolution of \texttt{<inheritdoc>} tags}
\label{sec:architecture-inheritdoc-resolve}

After all documentation comments are assigned, the \texttt{<inheritdoc>} tags are resolved.
First, it is important to remember that \texttt{<inheritdoc>} comments can be classified into three categories: those with the \texttt{cref} attribute, and those without it, which are further divided based on whether they are applied to a type or a member.
As explained in Section~\ref{sec:inheritdoc-resolve}, the resolution process begins by resolving all \texttt{<inheritdoc>} elements without the \texttt{cref} attribute and then proceeds with the ones that include it.

The following three classes handle the resolution, each responsible for resolving the corresponding kind of \texttt{<inheritdoc>} elements: \texttt{TypeInheritDoc\-Resolver}, \texttt{MemberInheritDocResolver}, and \texttt{CrefInheritDocResolver}.
In each of the three cases, the resolved documentation may again contain \texttt{<inheritdoc>} tags of the same kind, so the resolution must be done recursively.
Moreover, each of the cases can be viewed as a graph, where the nodes represent the types and members, whose documentation contains the \texttt{<inheritdoc>} tags of the given kind, while the edges indicate potential sources from which the documentation could be inherited.
Then, the depth-first search is performed to resolve the individual tags, one by one, while the graph itself is constructed on the fly, rather than being precomputed.
The recursion terminates when the parent node documentation has no \texttt{<inheritdoc>} elements of the given kind, i.e., there is nothing to resolve; in this case, the given \texttt{<inheritdoc>} tag is simply replaced by this XML.
The other terminal condition is when the parent node does not contain any documentation at all; then, the search continues with the other parent nodes.

It is important to understand that once we consider the DFS graph, the resolution of all kinds of \texttt{<inheritdoc>} tags is the same, as the only difference is what the nodes represent and how the set of parent nodes is obtained.
Therefore, the code performing the DFS is stored in the common base class, called \texttt{InheritDocResolver}, which has a single type parameter representing the type of the graph node.
The DFS results are cached, i.e., the \texttt{<inheritdoc>} elements contained in visited nodes are resolved as well.
Additionally, cycle detection is included as well.

Then, the \texttt{TypeInheritDocResolver}, \texttt{MemberInheritDocResolver}, and \texttt{Cref\-InheritDocResolver} 
inherit from the \texttt{InheritDocResolver} class, as shown in Figure~\ref{fig:inheritdoc-handlers},
and implement only the method responsible for obtaining the parent nodes of a node, along with other minor functionality. 
In \texttt{TypeInheritDocResolver}, the nodes represent the declared types, while the edges point to the base type and all implemented interfaces of a type.
Similarly, in \texttt{MemberInheritDocResolver}, the nodes correspond to the individual members, and the edges go to the equivalent definition of a member in the base type and all implemented interfaces.
Finally, the case of \texttt{CrefInheritDocResolver} is slightly different, as the nodes represent the individual XML comments. Then, the edge points to the documentation comment of the referenced type or member.

\section{Template processing}

In the next step, the \texttt{ITypeRegistry} is passed to a template processor and the resulting HTML is generated.
There is the \texttt{ITemplateProcessor} interface, which represents a contract for any template processor, and declares a single method, called \texttt{ProcessTemplates}, that accepts the \texttt{ITypeRegistry}, path to the output directory, and additional parameters.

The default implementation, called \texttt{RazorTemplateProcessor}, uses \textit{Razor} templates.
However, before the templates are processed, a handful of other tasks are performed, as illustrated in Figure~\ref{fig:razor-template-processor}.
First, the data from the type registry must be converted to the matching template models, which are then passed to the templates.
This transformation is executed by classes called \textit{template model creators}.
Additionally, all user-defined static pages must be gathered, which is done by the \texttt{StaticPageProcessor} class and then included in the documentation.
Furthermore, if a specific documentation version is generated, the versioning must be handled with the help of the \texttt{DocVersionManager} class.
The following sections describe each of these processes in further detail.

\subsection{Template models}
\label{sec:architecture-template-models}

The template models (TMs) are data-only objects that are passed to the templates as variables.
They correspond to the type and member objects stored in the type registry, as there is a separate template model 
for an object type, enum type, delegate type, and for each member (field, property, method, etc).
Likewise, there are template models for parameters, type parameters, and attributes.
Additionally, there are multiple other template models, representing namespaces, assemblies, etc.

Generally, a template model contains all the relevant information that will be included in the documentation. 
For example, the field template model (\texttt{FieldTM}) includes the name of a field, its type, modifiers, documentation comments, etc.
The member template models are then included within the type models; for instance, the template model for an object type, named \texttt{ObjectTypeTM}, includes its members (fields, properties, etc.) represented as template models.
Unlike the documentation of types and member objects contained in the type registry, the documentation comments in template models are represented as raw HTML strings.
It is also important to mention that the template models store language-specific data, for example, a collection of member modifiers, which differ for C\# and other languages.
These data are stored in fields of type \texttt{LanguageSpecificData<T>}, which essentially functions as a dictionary, indexed by language identifiers.

\subsubsection{Cross references}
\label{sec:architecture-cross-references-tms}

As requested by Requirement~\ref{req:cross-ref}, the generator supports cross-references.
This is achieved using the \texttt{CodeLinkTM} class, which encapsulates a type or member name, together with a URL to its definition.
The type or member name is stored as \texttt{LanguageSpecificData<T>}, as it may be displayed differently in each language.
Similarly to \texttt{CodeLinkTM}, there is the \texttt{GenericTypeLinkTM} class, which represents a type name and URL, along with the names and URLs of its generic parameters.
These template models are used to represent the type of a field, parameter, return type of a method, etc., and thus, creating cross-references in the templates is quite straightforward.

\subsection{Template model creators}
\label{sec:architecture-tm-creators}

The template model creators (TM creators) are used by the \texttt{RazorTemplate\-Processor} to create the individual template models.
There are multiple creators, as displayed in Figure~\ref{fig:tm-creators}; the
\texttt{ObjectTypeTMCreator}, \texttt{EnumTMCreator}, and \texttt{DelegateTMCreator} are responsible for creating the corresponding template models from the type data contained within the type registry.
For example, the \texttt{ObjectTypeTMCreator} converts the \texttt{IObjectTypeData} instance to its template model, named \texttt{ObjectTypeTM}, as shown in Figure~\ref{fig:object-tm-creator-workflow}.
During the process, all members contained within the type are converted to their template models as well.
All three creators mentioned above inherit from the \texttt{TypeTMCreator}, which contains the shared functionality, for instance, converting the attributes to their template model representation.

Additionally, there are \texttt{AssemblyTMCreator}, \texttt{NamespaceTMCreator}, \texttt{Search\-ResultTMCreator}, and \texttt{TopMenuDataTMCreator} creators, responsible for creating template models representing assemblies, namespaces, search page results, and top menu data.
Except for the \texttt{TopMenuDataTMCreator}, all of these classes inherit from the base class, named \texttt{BaseTMCreator}, which defines common logic used in all creators.

First, the \texttt{BaseTMCreator} class is responsible for creating the \texttt{CodeLinkTM} and \texttt{GenericCodeLinkTM} objects from the provided type data.
To get the URL, the \texttt{TypeUrlResolver} class, which is capable of obtaining the URLs of types contained in the type registry as well as the system types, is called.
The \texttt{TypeUrlResolver} first tries to find the provided type or member in the type registry.
If the given type or member is found, the URL of its page is returned. 
Next, if the type or member belongs to a standard library, the URL pointing to its page in the official .NET documentation is returned.
This URL can be easily constructed, as all page addresses in the .NET documentation follow the format described in the following Microsoft Learn article~\cite{official_docs_links}.

\subsubsection{Converting the inner XML tags to HTML}
\label{sec:architecture-inner-xml-to-html}

Another task performed by the \texttt{BaseTMCreator} is converting the documentation comments, represented as \texttt{XElement} instances, to their HTML representation, as displayed in Figure~\ref{fig:base-tm-creator}.
This involves replacing the inner XML tags with the corresponding HTML tags, since the template models store the documentation comments as HTML strings.
The transformation is handled by the \texttt{DocCommentTransformer} class, which accepts the \texttt{XElement} instance as input and works as follows:

First, a deep copy of the XML element is created, and all modifications are then performed on it.
Next, the XML tree is recursively searched, and if an inner XML tag is found, it is replaced with the corresponding HTML element.
The configuration that describes the mapping of inner XML tags to HTML is determined by the \texttt{IDocCommentHtmlConfiguration} interface, which is passed to the \texttt{DocCommentTransformer}.
This interface defines properties corresponding to the inner XML tags, while the values are the corresponding HTML elements, represented as \texttt{XElement} instances.
Each value could be a single element or a collection of nested elements.

The default configuration is provided by the \texttt{DocCommentHtmlConfiguration} class, whose visualization is shown in Listing~\ref{lst:html-config-visualization}.
As we can see, each HTML element is assigned a separate CSS class, starting with \textit{"refdocgen"}, which allows for easy styling using CSS.
Thus, the default configuration itself remains fully independent of any visual style and therefore could be used even in other than the default templates.

\begin{listing}[H]
\begin{lstlisting}[language=XML]
<list type="bullet"> => <ul class="refdocgen-bullet-list">
<list type="number"> => <ol class="refdocgen-number-list">
<para>               => <div class="refdocgen-paragraph">
...
\end{lstlisting}
\caption{\texttt{DocCommentHtmlConfiguration} -- visualization}
\label{lst:html-config-visualization}
\end{listing}

After the corresponding HTML element is obtained, the inner XML tag is replaced by it.
There is one special case, a \texttt{see} element with the \texttt{cref} attribute, as the type URL needs to be resolved in this case.
For this purpose, the \texttt{TypeUrlResolver} is used again, and a link is created.
If the referenced type or member is not found, instead of a link, a highlighted text is used.

After all inner XML tags are replaced, the resulting HTML is returned as a string.
Also, we can notice that the tags outside the set of inner XML tags are copied to the HTML as they are.
Thus, if the documentation contains, e.g., \texttt{<b>} or \texttt{<br>} elements, these tags are preserved and appear in the HTML as well.
It is also important to note that the \texttt{DocCommentTransformer} class is also used for converting the \texttt{<seealso>} elements to HTML, even though these belong to the top-level tags.
This is because they are processed almost identically as the \texttt{<see>} elements.

\subsubsection{Retrieving language-specific data}
\label{sec:architecture-lang-specifc-data-retrieval}

As mentioned earlier, the template models include language-specific data, such as type and member modifiers.
Thus, the template model creators must be capable of getting such data in all available languages.

In the codebase, each supported language is represented by a class implementing the \texttt{ILanguage\-Configuration} interface, which defines the contract for obtaining language-specific data.
More specifically, the interface declares methods for retrieving modifiers for various kinds of types and members, as well as methods for obtaining the type name, language identifier, and other relevant information.
The returned data are language-dependent; for instance, the modifiers are returned in a string array.

By default, there is only a single supported language -- C\#, as previously explained in Requirement~\ref{req:ui-multiple-langs}.
Its configuration class, called \texttt{CSharpLanguage\-Configuration}, provides the implementations of the methods mentioned earlier.
An array of available languages is passed to the \texttt{RazorTemplateProcessor} in its constructor, and then to the template model creators, which call the methods to obtain language-specific data, as illustrated in Figure~\ref{fig:tm-creators-langs}.

However, it is important to remember that the \texttt{ILanguage\-Configuration} and its implementations cover only part of the language-specific data, while the rest (such as printing type and member signature) is defined directly in the templates, as it typically requires various styling.

\subsection{Static pages}
\label{sec:architecture-static-pages}

Another responsibility of the \texttt{RazorTemplateProcessor} is to include user-defined static pages in the documentation.
Thus, the \texttt{RazorTemplateProcessor} has an optional constructor parameter, representing the path to the directory containing the pages and possibly other files.
There are two supported page formats: HTML and Markdown.

To obtain the page data, the \texttt{StaticPageProcessor} class is used, as shown in Figure~\ref{fig:static-pages-workflow}.
This class accepts the path to the static pages directory and recursively searches for files within it.
First, it locates all files in HTML and Markdown format and then processes them sequentially.
For HTML pages, the content is loaded as a string, along with the page path, and stored as a \texttt{StaticPage} instance.
On the other hand, the Markdown pages are first converted to HTML using the \textit{Markdig} library~\cite{markdig} and similarly converted to \texttt{StaticPage} instances.
Additionally, while creating a \texttt{StaticPage} instance, the page content is browsed, and all links pointing to Markdown files are updated to reference the corresponding HTML file.
Then, the page data is returned.

Later, the \texttt{RazorTemplateProcessor} puts the content of individual pages into a template, which defines the layout of static pages, and thus generates the resulting HTML.
Other files contained in the static pages folder (such as images and JavaScript files) are copied as they are to the output folder.
The structure of the static pages directory is preserved, meaning that each page is stored in a file whose path within the output directory matches the original path in the static pages folder. 
As a result, the relative links between the static files stay the same.

\subsection{Documentation versioning}
\label{sec:architecture-doc-versions}

Additionally, the \texttt{RazorTemplateProcessor} handles creating specific versions of the documentation. 
For this reason, it has an additional optional constructor parameter identifying the version being created.
When a specific version is created, it is not stored directly in the output directory, but in its subfolder named after the version identifier.
Hence, the \texttt{v1.0} version gets stored in the \texttt{output/v1.0} directory.
Additionally, each resulting HTML page stores a list of its available versions.
As explained in Section~\ref{sec:documentation-versioning-three}, the data are stored as a JSON list inside a visually hidden element, whose id is \texttt{version-list}.
Then, when the page is loaded, the data is handled using JavaScript.

Before the documentation is generated, the \texttt{RazorTemplateProcessor} calls the \texttt{DocVersionManager} class to obtain a list of available versions for the individual pages.
The data describing individual versions is stored in the \texttt{versions.json} file in the output directory.
As illustrated in Listing~\ref{lst:versions-json}, this file stores the version identifier together with the array of generated pages.
The \texttt{DocVersion\-Manager} first loads the JSON file and, using its data, the list of available versions for each page is returned.

After the documentation is created, the \texttt{DocVersionManager} is called again. 
This time, it updates the JSON to include the latest version data.
Additionally, the corresponding older versions of the documentation must be updated to include the most recent version.
Thus, the individual HTML pages of older versions are one by one loaded and then, using the \textit{AngleSharp} library~\cite{anglesharp}, the \textit{version-list} HTML element is located and the most recent version identifier is added to the list.

\subsection{Templates}
\label{sec:architecture-eight-templates}

The \texttt{RazorTemplateProcessor} class has eight generic parameters, representing the types of the individual Razor templates, as shown in Figure~\ref{fig:eight-templates}.
The \textit{Object type} template is intended to display all relevant information about an object type, including its documentation as well as a list of its members with documentation comments.
Similarly, the \textit{Enum} and \textit{Delegate} templates should display all relevant data of an enum or a delegate, respectively.
The \textit{Namespace} and \textit{Assembly} templates are expected to display a list of all types contained within a namespace or an assembly, respectively.
Next, the \textit{API homepage} template should serve as a homepage of the API, showing all types across the provided assemblies.
Finally, the \textit{Static page} template provides a template for all user-defined static pages, while the \textit{Search page} template is intended to perform searching and display search results.

It is crucial to remember that the \texttt{RazorTemplateProcessor} defines the overall page structure of the documentation; however, the individual templates are not hard-coded, and thus, custom templates may be provided.

\subsubsection{Template variables}
\label{sec:architecture-template-vars}

To create the resulting HTML pages, the \texttt{RazorTemplateProcessor} needs to pass the individual template models to the corresponding templates.
Hence, for example, the \texttt{ObjectTypeTM} instances are one by one passed to the \textit{Object type} template.
This way, a separate HTML page is created for every object type.
Thus, each of the templates, except the \textit{Static page} template, is expected to have a parameter representing its template model, named \texttt{Model}.
Additionally, the following variables are passed to all templates (including the \textit{Static page} template):

\begin{itemize}
    \item \texttt{TopMenuData} -- specifies the links and folders contained within the top menu.
    \item \texttt{Languages} -- an array of the available languages.
    \item \texttt{Versions} -- an array containing the available versions of the page.
    \item \texttt{ProjectName} -- name of the assembly/project/solution being documented.
\end{itemize}

On top of that, three other variables are passed exclusively to the \textit{static page} template:
\begin{itemize}
    \item \texttt{CustomStyles} -- path to the custom CSS file, contained in the static pages folder.
    \item \texttt{NestingLevel} -- the nesting level of the static page.
    \item \texttt{Contents} -- HTML contents of the static page body.
\end{itemize}

\subsubsection{Output directory structure}
\label{sec:output-dir-structure}

The \texttt{RazorTemplateProcessor} stores all \textit{type}, \textit{namespace}, and \textit{assembly} pages to the \texttt{api/} subfolder of the output folder, while the HTML file names match the IDs of the template models.
For a namespace template model, its ID corresponds to the namespace name; similarly, for assemblies, it matches the assembly name, with the only difference being that it has the suffix \textit{-DLL}.
The ID of any type template model is almost equivalent to its ID string used in the \texttt{TypeRegistry}; as the only difference is that some characters need to be escaped, which is handled by the \texttt{TemplateId} class.
Next, the API homepage is stored as \texttt{api/index.html}, while the search page is stored directly in the output directory as \texttt{search.html}.
Finally, each user-defined static page is stored in a file whose location matches the static page location within the static pages directory, as explained in Section~\ref{sec:architecture-static-pages}.
Additionally, if the folder with Razor templates also contains a directory named \texttt{Static}, this directory gets copied as it is to the output folder.

\section{Default templates}
\label{sec:default-templates-overview}

The default \textit{Razor} templates are stored in the \texttt{refdocgen/src/RefDocGen/Template\-Processors/Default/Templates} directory.
There are eight top-level templates: \texttt{ObjectTypePage}, \texttt{EnumTypePage}, \texttt{DelegateTypePage}, \texttt{NamespacePage}, \texttt{Assem\-blyPage}, \texttt{ApiHomePage}, \texttt{StaticPage}, and \texttt{SearchPage}, which correspond to the generic parameters of the \texttt{RazorTemplateProcessor} class, described in Section~\ref{sec:architecture-eight-templates}.
Each of the templates accepts the parameters outlined in Section~\ref{sec:architecture-template-vars}; however, only the \texttt{Model} parameter is typically used directly in the template itself.
Other parameters, such as \texttt{TopMenuData}, are usually passed to descendant components as cascading values, which are explained in further detail in the official documentation~\cite{razor_cascading_values}.
The entire UI is composed of many reusable components; for example, the documentation of parameters is stored within a separate component, which is then reused by methods, operators, and constructors.

\subsubsection{Layout}

The layout, which is shared between all pages, is defined in the \texttt{AppLayout} component.
It specifies both top and bottom menus; thus, each of the eight top-level pages defines only the content displayed in the page body.
The cascading values, for instance, \texttt{TopMenuData}, are typically consumed either by the layout itself or by one of its descendant components.

\subsection{UI styling}
\label{sec:ui-styling}

As discussed in Section~\ref{sec:tech-analysis-ui-framework}, the components and styles provided by the \textit{Bootstrap} framework~\cite{boostrap} are used for styling the user interface.
For example, the top menu, as well as the links, make use of the \textit{Bootstrap} classes; furthermore, \textit{Bootstrap} also ensures the responsiveness of the UI.
In addition to the styles provided by \textit{Bootstrap}, several custom CSS rules are defined in the \texttt{Scss/styles.scss} file.
As the file name suggests, the styles are written in the \textit{Sass}~\cite{sass} format, rather than plain CSS, which enables us to use additional functionality on top of CSS.

The \texttt{styles.scss} file first loads all \textit{Bootstrap} styles, using the \texttt{@use} rule.
Then, several custom CSS rules, often extending the \textit{Bootstrap} classes using the \texttt{@extend} rule, are declared.
This way, several of the transformed inner XML tags, described in section~\ref{sec:architecture-inner-xml-to-html}, are styled.
For example, the \texttt{.refdocgen-see-cref} class, which is assigned to the transformed \texttt{<see cref="...">} XML tags, is configured to extend the \texttt{link-offset-2} CSS class, provided by \textit{Bootstrap}.

After every change, the SCSS must be recompiled manually to create the final CSS using the \texttt{sass Scss/styles.scss Static/styles.css --style=com\-pressed} command executed from the default templates folder.
This way, both the custom and the \textit{Bootstrap} styles get stored in the \texttt{Static/styles.css} file, which is then referenced from the templates.

\subsection{Documentation themes}
\label{sec:ui-themes}

The documentation supports both light and dark themes by using the \texttt{data-bs-theme} attribute, provided by \textit{Bootstrap}.
This attribute, assigned to the \texttt{<html>} element, can be set to either \texttt{light} or \texttt{dark} value.
When set to a given value, all elements in the document are automatically styled accordingly.
Furthermore, the text color classes, mentioned in the previous section, change their appearance based on the selected theme, as specified in the \texttt{styles.scss} file.
For example, any text styled with \texttt{refdocgen-text-primary} class is displayed in black when using the light mode, and in white when the dark mode is used.

The theme can be switched using the corresponding button in the top menu.
When the button is clicked, a custom JavaScript handler is executed, which sets the \texttt{data-bs-theme} attribute to the given value.

\subsection{Language-specific fragments}
\label{sec:ui-language-fragments}

The templates need to display language-specific fragments, for instance, the declarations of the individual types and members, as the syntax differs between various languages.
Furthermore, unlike the language-specific data described in Section~\ref{sec:architecture-lang-specifc-data-retrieval}, these data require various styling, as, for instance, the member modifiers should be displayed in a different color than the member name and type.
Therefore, each language must define a separate set of \textit{Razor} components that represent these language-specific fragments.

The components for a given language are stored within a subfolder of the \texttt{Components/LanguageSpecific} folder, whose name is specified in the corresponding language template model.
For example, the components for C\# are stored within the \texttt{CSharp} folder.
The project also includes the \texttt{Todo} folder containing empty components, which serve as a starting point when adding support for a new language.

Each folder then contains the language-specific components, each corresponding to one of the 15 values of the \texttt{LanguageSpecificComponent} enum, which describes the places where language-specific data are displayed.
All of these components have a single parameter, typically the template model, that is being displayed.
Additionally, each template must be named after the matching \texttt{LanguageSpecificComponent} value, with the only difference being that it is prefixed with the folder name.
For instance, the component representing the \texttt{LanguageSpecificComponent.FieldDeclaration} fragment in C\# is named \texttt{CSharpFieldDeclaration}.
The individual components then display the given data in the selected language; thus, e.g., the \texttt{CSharpFieldDeclaration} displays a field declaration using C\# syntax.
As previously described in Section~\ref{sec:ui-text-colors}, various colors are often used for different data.

Displaying of all language-specific fragments is handled by the \texttt{Language\-Fragments} component, which has the following two parameters:

\begin{itemize}
    \item \texttt{Type} -- a value of the \texttt{LanguageSpecificComponent} enum describing which language-specific fragment should be rendered.
    \item \texttt{Parameter} -- an object that is passed to the fragment component as a parameter.
\end{itemize}

Hence, for example, to render a field declaration, we need to pass the \texttt{Language\-SpecificComponent.FieldDeclaration} value, together with the template model of the field, as displayed in Figure~\ref{fig:lang-fragments}.
Additionally, the \texttt{LanguageFragments} component also uses the \texttt{Languages} cascading value, introduced in Section~\ref{sec:architecture-template-vars}, to obtain all languages.
Then, it simply renders the given fragment in all available languages.
The corresponding component for each language is found automatically by its name and rendered as a 
\textit{DynamicComponent}, which is explained in more detail in the official documentation~\cite{aspnet_dynamic_component}.

\subsubsection{Displaying the fragments in the selected language}
All HTML elements representing the language-specific fragments are, by default, hidden and have the \texttt{data-language} attribute set to the corresponding language ID.
Thus, for example, the C\# fragments are marked with the \texttt{data-language="csharp-lang"} attribute.
In addition to that, the \texttt{<html>} element also has the \texttt{data-language} attribute, which indicates the currently selected language.

Next, we have defined the following CSS rule, which selects the following elements:
\texttt{html[data-language=XX] [data-language=XX]}, where \texttt{XX} is the language ID, and makes them visible.
Such a rule is defined programmatically, using \textit{Razor}, for each of the available languages.
This way, only the fragments in the currently selected language are displayed.

\subsubsection{Switching the language}
\label{sec:ui-langauge-switching}

The language in which the language-specific fragments are displayed is selected using a dropdown, which gets populated with the \texttt{Languages} data, mentioned in Section~\ref{sec:architecture-template-vars}. 
When a language is selected, a custom JavaScript handler is executed, similarly to when switching themes.
The selected language identifier is then assigned to the \texttt{data-language} attribute of the \texttt{<html>} element, which makes the language-specific fragments in the given language visible.

\subsection{Persisting the selected theme and language}

In Section~\ref{sec:ui-themes}, we described that when the theme is switched, the value of the \texttt{data-bs-theme} attribute is updated accordingly by a JavaScript function.
Since we want to persist this value, the selected theme is also saved to the local storage of the browser under the \texttt{refdocgen-theme} key; however, this applies only if the documentation is deployed on a server.
On the other hand, if the documentation is created locally and thus accessed using the \textit{file} protocol, this does not work, because the local storage has undefined behavior in such cases, as explained in the MDN Web documentation~\cite{mdn_localstorage}.
For that reason, if the documentation is created locally, the selected theme gets stored in the \texttt{theme} URL parameter.
Similarly, for languages, the selected language identifier is stored either in the local storage under the \texttt{refdocgen-language} key or in the \texttt{lang} URL parameter, based on where the documentation is deployed.

Additionally, if the documentation is created locally, all links within the documentation must be updated to include the correct URL parameters.
Thus, a custom JavaScript function, named \texttt{updateRelativeLinks}, is called when a page is loaded.
This function finds all relative links in the document (i.e., the \texttt{<a href="..">} elements) and appends the \texttt{theme} and \texttt{lang} parameters to the target URLs.

Next, there is another JavaScript function that is executed before each page is loaded.
This function checks whether the selected theme and language values are stored in local storage (if the documentation is deployed on a server) or in the URL parameters (if the documentation is created locally).
If a value is not found, the default option is used, and then, the \texttt{data-bs-theme} and \texttt{data-language} attributes are set accordingly.
This way, it is ensured that the selected theme and language remain the same when navigating within the documentation.

\subsection{Documentation versioning}
\label{sec:default-ui-version-dropdown}

As already described in Section~\ref{sec:architecture-doc-versions}, each page contains the \texttt{version-list} HTML element, which is hidden and stores the array of available page versions as JSON.
Once the page is loaded, custom JavaScript reads this data and populates the version selector dropdown accordingly.
Each item in the dropdown represents a link to the corresponding version of the page.
It is also worth noting that redirecting to a different version of the page is straightforward, as it only requires updating the part of the URL that contains the version identifier.

\subsection{Searching the documentation}
\label{sec:default-ui-search}

The search functionality is provided on the search page.
An array of all possible search results -- i.e., all types, members, namespaces, and assemblies is stored as JSON in a hidden element, similarly to the array of page versions.
Each item contains the name, summary documentation (if provided), and additional data.
It is important to note that in the case of members, only the name is included; specifically, no parameters are contained.
As a consequence, if a method has multiple overloads, only one of them is included in the search results.

Every time a character is typed into the search box, a JavaScript-based fuzzy search is performed using the \textit{Fuse.js} library~\cite{fuse_js}.
The search runs on the names of the individual items (i.e., types, members, namespaces, and assemblies), and the matching results are then displayed below.

\section{Error handling}

The program detects errors caused by invalid configuration.
A custom base exception, named \texttt{RefDocGenFatalException}, is used to represent those types of errors.
Then, there are several custom exceptions inheriting from it; for instance, 
the \texttt{AssemblyNotFoundException} is thrown if the assembly is not found at the user-provided path.
Similarly, the \texttt{DuplicateDocVersionNameException} is thrown if the user specifies an already existing documentation version name.
All of these custom exceptions include descriptive error messages designed to be displayed to the user.
Finally, all exceptions are caught in the \texttt{Main} method and logged as errors.

The logging is handled by a \textit{Serilog}~\cite{serilog} logger instance, configured to print on the command line.
However, the logger is passed as an \texttt{ILogger} interface, which is a common logger interface provided by Microsoft, as further explained in the documentation~\cite{net_ilogger}.
As a result, the classes using the logger depend only on its interface, rather than on the concrete \textit{Serilog} implementation.

\section{Tests}

The project is tested by both integration and unit tests, which are contained in 
\texttt{RefDocGen.IntegrationTests} and \texttt{RefDocGen.UnitTests} projects.
Both of them use the \textit{xUnit}~\cite{xunit} testing framework and \textit{Shouldly} library~\cite{shouldly} for assertions.

\subsection{Integration tests}
The integration tests check whether the generated documentation looks as expected.
As shown in Figure~\ref{fig:integration-tests-architecture}, they use the DLL and XML documentation file of the \texttt{RefDocGen.ExampleLibrary}, which is intended purely for integration testing.
Similarly, the DLLs and documentation of \texttt{RefDocGen.ExampleFSharpLibrary} and \texttt{RefDocGen.ExampleVbLibrary} libraries are used as well.

Most of the integration tests are part of the \texttt{DocumentationTestCollection}, which is an \textit{xUnit} collection fixture responsible for creating the reference documentation.
The \texttt{DocumentationTestCollection} uses the DLL and XML documentation file of the \texttt{ExampleLibrary} and simply calls the \texttt{DocGenerator} class, mentioned in Section~\ref{sec:workflow}.
Thus, before all tests are run, the documentation is generated, and after the tests terminate, the folder with the documentation is deleted.
There is also the \texttt{VersionedDocumentationTestCollection} collection fixture, which creates documentation with multiple versions and is used by a handful of other tests.

\begin{figure}[H]
\centering
\includegraphics[width=0.8\linewidth]{img/integration-tests.png}
\caption{Integration tests -- architecture}
\label{fig:integration-tests-architecture}
\end{figure}

To simplify testing, the default templates assign the \texttt{data-id} attribute to each relevant HTML element.
For instance, all elements containing \textit{remarks} documentation comments have the \texttt{data-id="remarks-doc"} attribute.
Furthermore, each member on the type page can be located by its \texttt{id} attribute.

Most of the tests verify the type and member declaration strings, as well as the individual documentation comments.
Additionally, tests checking the inheritance of documentation comments are also included.
Many of the tests are parametrized, which enables us to test multiple cases with a single piece of code.
The individual test classes are named after what is being tested; e.g., the class verifying the member documentation is called \texttt{MemberDocCommentTests}.
Then, the test methods are typically named as follows: \textit{Subject\_ExpectedOutcome}.
The \textit{Subject} describes what is being tested, while the \textit{ExpectedOutcome} describes what the \textit{Subject} should satisfy.
Thus, for example, the method responsible for verifying the \textit{remarks} documentation of a member is named \texttt{RemarksDoc\_Matches}.

The test methods, in most cases, first locate the selected page in the output directory, parse it using the \textit{AngleSharp} library, and then select the given element, based on its \texttt{data-id}.
For instance, the test verifying the remarks documentation of the given member would first locate the page of the containing type, parse the HTML, find the given member (by its \texttt{id}), and then obtain the corresponding \textit{remarks} documentation (i.e., an element with \texttt{data-id="remarks-doc"}).
Then, it is checked whether the content of the element is as expected.

\subsection{Unit tests}

Furthermore, selected pieces of code are tested using unit tests.
The unit test classes are mapped one-to-one with the project classes, and additionally, each test class is named the same as the corresponding project class, with the only exception being that it ends with the suffix \textit{Tests}.

Additionally, the folder structure of the unit tests project aligns with the structure of the main project.
It is also worth noting that the unit tests frequently use mocking, with the help of \textit{NSubstitute} library~\cite{nsub}, as previously discussed in Section~\ref{sec:tests-mocking-explanation}.

\section{Code quality}

This section describes the conventions and practices that ensure the code quality of our program.

\subsection*{.NET Analyzers}

First, we use the built-in .NET analyzers~\cite{net_analyzers}, via the \textit{Microsoft.CodeAnalysis.NetAnalyzers} NuGet package, while using the recommended level of settings.
As a result, we receive more warnings related to code quality.
Additionally, the .NET analyzers are also used to enforce a consistent code style across the codebase, based on the defined code style rules.
Except for a few exceptions, specified in the \texttt{.editorconfig} file in the root folder, the default code style is used.
For example, we have configured the system to use type inference when possible, except in cases where the type is one of the built-in types.
 
\subsection*{Workflow}
The project is hosted in a public GitHub repository at the following URL: \url{https://github.com/VL-CZ/refdocgen}.
When developing, we use the following conventions.
For each task, we first create a separate branch, named \textit{feature/XX-description}, where \textit{XX} refers to the task ID, and \textit{description} is a brief description of the task, with words separated by dashes.
Once the work is completed, we create a pull request, named \textit{[T-XX] description}.
Similarly to branches, \textit{XX} is the task ID; however, the description is now written in the English language.
Thus, regarding the task with ID 25, which is about adding support for enums, the branch name could be \textit{feature/25-add-enum-support}, while the PR name would be \textit{[T-25] Add support for enums}.

Before each pull request is merged, we use \textit{GitHub Actions}~\cite{github_actions} to perform continuous integration checks.
There is a single workflow, configured using the \texttt{.github/workflows/dotnet.yml} file.
First, the project is built, while all warnings (including those for code quality) are treated as errors.
Then, both unit and integration tests are executed, and finally, the code style is verified.
If and only if all of these checks pass, the pull request can be merged to the \textit{master} branch.
The merge is configured to use squashing; thus, each PR results in a single commit, whose name matches the name of the PR, in the \textit{master} branch.
This way, a linear history of the \textit{master} branch is achieved.

\section{Extensibility}

This section describes how the program can be extended.
Specifically, users may provide custom \textit{Razor} templates, template processors, or add support for a new language to the default UI.

\subsection{Custom Razor templates}
\label{sec:extensibility-custom-razor}

It is possible to use custom \textit{Razor} templates, instead of the default ones, with the \texttt{RazorTemplateProcessor} class, as previously mentioned in Section~\ref{sec:architecture-eight-templates}.
This allows us to declare a custom UI; however, the overall structure of the documentation remains the same as when the default templates are used.
Likewise, the output folder structure remains as described in Section~\ref{sec:output-dir-structure}.

To add custom \textit{Razor} templates, we first navigate to the \texttt{TemplateProcessors} folder in the \texttt{RefDocGen} project, copy the \texttt{Todo} subfolder, and rename it to reflect the design of the templates (for example, \texttt{RazorMinimal}).
Next, we provide the implementation of the eight \textit{Razor} templates, located in the \texttt{Templates} subfolder.
Each template includes a description of its intended usage and parameters.
We may design the UI arbitrarily and use any UI framework of our choice; however,
several points should be taken into account:

\begin{itemize}
    \item All template parameters must stay the same.
    \item The HTML elements representing members on type pages should have the \texttt{id} equal to the member ID.
    \item The \texttt{Templates/Static} folder gets copied as it is into the output directory.
    Thus, if we want to provide custom CSS and JavaScript, we should place them here.
    Ideally, we should use the provided \texttt{styles.css} and \texttt{script.js} files.
    \item To support versioning, each page must contain an HTML element with the \texttt{id="version-list"}.
    The JSON array of available version identifiers will be automatically inserted there, as described in Section~\ref{sec:architecture-doc-versions}.
    Then, when the page is loaded, we can process these values using JavaScript, and, for example, insert them into a dropdown, similarly to the default UI. 
    \item Some of the data, such as field modifiers, are represented as objects of \texttt{LanguageSpecificData<T>} type, 
which works as a dictionary, indexed by language IDs.
Currently, only the C\# language is supported; thus, to obtain C\# data, we can use the \texttt{LanguageSpecificData<T>.CSharpData} property.
Optionally, the templates may be designed to be extensible for adding new languages, similarly to the default UI, as described in Section~\ref{sec:ui-language-fragments}.
\end{itemize}

It is recommended, although not mandatory, to get inspiration from the default templates, described in Section~\ref{sec:default-templates-overview}, and compose the UI of many reusable components as well.
However, it is typically not possible to reuse the components from the default UI, because they already use the \textit{Bootstrap} framework.
In addition to the templates, it is necessary to configure the style of the inner XML tags transformed to HTML, as explained in Section~\ref{sec:architecture-inner-xml-to-html} in greater detail.
There are two options: to reuse the default configuration or create a custom one.

If the default configuration does not suit our use case, we need to create a new configuration that defines a custom mapping between the inner XML tags and the target HTML elements.
To do this, we first need to create a class named, for instance, \texttt{RazorMinimalConfiguration}, which implements the \texttt{IDocCommentHtmlConfiguration} interface, and place it into the \texttt{RazorMinimal} folder.
Then, we need to implement the properties defined by the interface.
The configuration uses a declarative approach, so each property represents the target HTML for the given XML tag.
Hence, if we want the \texttt{<c>} XML tag, representing inline code, to be replaced by the \texttt{<span class="my-class">} HTML element, we should use the code shown in Listing~\ref{lst:extensibility-custom-html}.

     ...

There are several other points we need to keep in mind:

\begin{itemize}
    \item For the links, it is not mandatory to specify the \texttt{href} attribute in the configuration, as it is added automatically.
    \item It is generally fine to use concrete CSS classes in the custom configuration, because it is not likely to be reused, unlike the default configuration.
    \item If we wanted to update a couple of target HTML elements in the default configuration, while keeping the rest as it is, there is another approach we can use.

\subsection{Custom template processor}
\label{sec:extensibility-custom-template-processor}

Another way to customize the output is to use a custom template processor.
When doing this, we are no longer limited to \textit{Razor} templates, as we may use any templating language of our choice.
Similarly, the output format does not have to be HTML, as we can generate, e.g., the documentation in Markdown format.

First, we need to create a custom template processor class, which implements the 
\texttt{ITemplateProcessor} interface.
To do this, we open the \texttt{RefDocGen} project, navigate to \texttt{TemplateProcessors} folder and create a new folder, named, e.g., \texttt{Custom}.
Inside this folder, we create a class, named \texttt{CustomTemplateProcessor}, for instance.
This class must implement the \texttt{ITemplateProcessor} interface, which has a single method, \texttt{ProcessTemplates}, which is expected to create the documentation based on the data provided in the type registry.

Then, we need to add the implementation, which may be arbitrary; however, it is a good idea to follow these recommendations:

\begin{itemize}
    \item It is preferred to keep all the related code in the same folder (i.e., \texttt{Custom} in our case) or in its subfolders.
    \item If the template processor requires additional parameters, we should pass them in the constructor.
    \item If the documentation generation fails, it is recommended to throw an exception with a descriptive message.
    \item Optionally, the processor may be designed in a way that allows users to provide custom templates, similarly to the \texttt{RazorTemplateProcessor}.
\end{itemize}

\subsubsection{Reusing existing classes}

If the documentation output is HTML, we can reuse the \texttt{StaticPageProcessor} class, described in Section~\ref{sec:architecture-static-pages}, to collect the static pages provided by the user.
Similarly, the \texttt{DocVersionManager} class, introduced in Section~\ref{sec:architecture-doc-versions}, might also be used in the custom template processor.
The only requirement is that each HTML page in the documentation must contain an element with the
\texttt{id="version-list"}, where the JSON array of available page versions will
be automatically placed.
Moreover, the \texttt{DocCommentTransformer} class, described in Section~\ref{sec:architecture-inner-xml-to-html} as well as its default configuration, explained in Section~\ref{sec:extensibility-custom-razor}, might be reused too.

Additionally, if the following two conditions hold, it is possible to reuse even the template model creators, described in Section~\ref{sec:architecture-tm-creators}.

\begin{enumerate}
    \item The default template models, mentioned in Section~\ref{sec:architecture-template-models}, suit us well and we would like to use them in the templates.
    \item The resulting documentation is designed to have the same output structure as the default templates. Thus, each type, namespace, and assembly is represented by a separate page, stored in the \texttt{api} folder. The page URL should be equal to the corresponding template model ID, as previously explained in Section~\ref{sec:output-dir-structure}.
    Additionally, on type pages, each member element should have the \texttt{id} attribute set to the corresponding member ID.
\end{enumerate}

In this case, the entire process of generating HTML is similar to that of the \texttt{RazorTemplateProcessor}, with the only difference being that another templating language is used.
For this reason, it is recommended to use the \texttt{RazorTemplate\-Processor} class as a reference.
Additionally, it is important to remember that the default template models store selected data as language-specific, as noted in the fifth bullet point in Section~\ref{sec:extensibility-custom-razor}.

\subsubsection{Registering the template processor}

Next, we need to register the template processor class, which is very similar to registering custom \textit{Razor} templates, described in Section~\ref{sec:extensibility-register-custom-razor}.
In the \texttt{Program.cs}, we locate the comments marked with \texttt{\#ADD\_TEMPLATE\_PROCESSOR}.
First, we need to add a new \texttt{DocumentationTemplate} enum value, corresponding to the custom template processor.
Then, we must add the template processor to the set of available documentation templates.
As stated in the second comment, this is done by adding an instance of the processor to the dictionary of available documentation templates, while the previously selected \texttt{DocumentationTemplate} value should be the key.
Following that, the template processor is registered and added to the list of available documentation templates, displayed on the command line.

\subsection{Adding a new language}
\label{sec:extensibility-new-lang}

When adding support for a new language to the default UI, we first need to create a configuration class for the language and then provide \textit{Razor} components representing the language-specific fragments in the given language.

\subsubsection{Creating new language configuration}

To create a language configuration, we first need to open the \texttt{RefDocGen} project and navigate to the \texttt{TemplateProcessors/Shared/Languages} directory.
Next, we create a copy of the \texttt{TodoLanguageConfiguration.cs} file and rename it (including the contained class) to, e.g., \texttt{MyLanguageConfiguration.cs}.
This class defines methods for obtaining selected language-specific data, such as modifiers, type names, 
and other relevant information, for the given language, as previously mentioned in Section~\ref{sec:architecture-lang-specifc-data-retrieval}.

In the next step, we add the implementation, following the documentation comments provided for each method and property.
Specifically, when returning the modifiers, we should keep in mind that this is the preferred place to define their order and return them accordingly.
In case of any doubts, it may be helpful to refer to the default C\# configuration, represented by \texttt{CSharpLanguageConfiguration} class, for guidance.

Finally, the configuration must be added to the collection of supported languages.
To do this, we need to locate the comment marked with \texttt{\#ADD\_LANGUAGE} in the \texttt{Program.cs} and instantiate the language configuration there, as described in the source code.
As a result, \texttt{MyLanguageConfiguration} will be included in the list of available language configurations.

\subsubsection{Creating language-specific components}

Additionally, we need to create \textit{Razor} components representing the language-specific fragments of the default UI, such as field declarations, displayed in the given language.
It is important to note that this cannot be done in the language configuration itself, as the fragments typically require different styling to display modifiers, member names, etc., in various colors.
We start by navigating to the \texttt{TemplateProcessors/Default/Templates/Components/LanguageSpecific} directory, which contains a subdirectory with language-specific components for each supported language.
Next, we copy the \texttt{Todo} directory and rename it, so that its name matches the \texttt{ComponentsFolderName} property of the previously created language configuration.
Thus, if we set the \texttt{ComponentsFolderName} to \texttt{"MyLang"}, the folder must be named \texttt{MyLang}.
Moreover, each component inside the folder must be renamed to start with \texttt{MyLang} instead of \texttt{Todo}.
Hence, for example, the \texttt{TodoFieldDeclaration} component needs to be renamed to \texttt{MyLangFieldDeclaration}.

Following that, we need to add the code to each component, which defines how the corresponding fragment is displayed in the given language.
There is a comment inside each component, which specifies what should be rendered; it is also possible 
(and recommended) to get inspiration from the default C\# templates, stored in the \texttt{CSharp} folder.
Also, a few points should be kept in mind:

\begin{itemize}
    \item The component parameters must remain unchanged.
    \item The font size and weight are set automatically, as the rendered component is put inside a pre-styled \texttt{<span>} element, which also means that the component content should be inline.
    \item However, the text coloring needs to be defined manually, and
it is advised to use the same color scheme as the default C\# fragments. 
Hence, the \texttt{refdocgen-text-primary} CSS class should be used for type and member names, while
for member, parameter, and return types, as well as for the type parameters, we should use the \texttt{refdocgen-text-secondary} and \texttt{refdocgen-link-secondary} classes (depending on whether the link is found or not).
Additionally, it is preferred to use the \texttt{refdocgen-text-tertiary} class for displaying modifiers.
    \item Finally, as explained in Section~\ref{sec:architecture-template-models}, some of the data, such as field modifiers, are represented as objects of \texttt{LanguageSpecificData<T>} type, 
which works as a dictionary, indexed by language IDs.
To access the data in the given language, we need to know the \texttt{LanguageId}, defined in the language configuration.
If we use, for example, the \texttt{"my-lang"} as the ID, we can access the field modifiers for this language by calling \texttt{field.Modifiers["my-lang"]}.
\end{itemize}

This way, the language is added to the default UI.

\section{Installation}

There is a single prerequisite: having .NET 8 (or higher) installed.
The preferred way to install \textit{RefDocGen} is via NuGet as a global .NET tool~\cite{dotnet_tools}, using the following command:
\texttt{dotnet tool install --global RefDocGen}.
This makes the \texttt{refdocgen} command available on the command line.
Alternatively, it is also possible to clone the project from GitHub and run it using \texttt{dotnet run}, although this is recommended only for development purposes.

It is important to remember that \textit{RefDocGen} does not support .NET Framework projects. 
However, this limitation is not significant, as the intended usage of our program is to generate reference documentation of \textit{NuGet} packages, 
which in the vast majority of cases target .NET or .NET Standard.

\subsubsection*{Additional options}

We can select the output directory, using the \texttt{-o} flag.
Next, the \texttt{-t} option allows us to select a documentation template. 
Currently, only the default template is available; however, it is possible to add custom documentation templates, as further described in sections~\ref{sec:extensibility-custom-razor} and~\ref{sec:extensibility-custom-template-processor}.

When the \texttt{-v} flag is specified, the log level is set to verbose; thus, all log events are displayed.
Before describing the \texttt{-f} flag, it is important to note that the program intentionally fails
if the output directory exists and is not empty (and the documentation is not versioned) to prevent users from accidentally overwriting data.
To override this behavior, and thus delete the output directory before the documentation is generated, the \texttt{-f} flag can be used.
Next, using the \texttt{-s} flag, the current configuration can be saved to a YAML file, as explained in section~\ref{sec:user-docs-yaml} in more detail.
Additionally, it is possible to provide custom static pages as well as create a specific version of the documentation 
by specifying the \texttt{--static-pages-dir} and \texttt{--doc-version} options, respectively, as further described in sections~\ref{sec:user-docs-static-pages} and~\ref{sec:user-docs-versions}.

Next, it is possible to configure which types and members are included in the documentation.
Using the \texttt{--min-visibility} flag, we can select only the members with the given visibility or higher.
Additionally, we can select which inherited members should be included by specifying the \texttt{--inherit-members} option.
When set to \texttt{None}, no inherited members are contained in the documentation, while when using \texttt{All}, the documentation displays all inherited members.
However, in most cases, we would likely want to include all inherited members, except those inherited from the \texttt{object} type, 
such as the \texttt{ToString()} method, which can be achieved by using the default value (i.e.,  \texttt{NonObject}).

Furthermore, the \texttt{--exclude-projects} option allows us to exclude certain projects from the documentation; thus, any types and members defined in these projects will not be included.
Naturally, using this option makes sense only if the input is a solution.
Similarly, we can exclude certain namespaces from the documentation.
In this case, it is important to remember that any child namespaces will also be excluded.
Thus, if we choose to exclude the \texttt{MyApp.Tools} namespace, for instance, the \texttt{MyApp.Tools.Text} namespace will be excluded as well.
Both of these options may have multiple values, separated by spaces.

\subsection{Adding static pages}
\label{sec:user-docs-static-pages}

Custom static pages, such as \textit{index} or \textit{FAQ} page, can be added to the documentation.
To do this, we need to create a directory and
store the pages inside it (or its subdirectories) in either HTML or Markdown format.
For each page, we should specify only the body content (without the \texttt{<body>} element), as the documentation layout is added automatically.
Then, when creating the documentation, we need to use the \texttt{--static-pages-dir} option and pass this directory as its value.
As a result, each of the pages will be included in the reference documentation.
All relative paths between the files remain unchanged; therefore, we can safely use relative links to navigate to different pages.

An example static pages directory is shown in Listing~\ref{lst:static-pages-dir-example}, while
the individual pages are displayed in Listings~\ref{lst:example-static-page1} and~\ref{lst:example-static-page2}.

\begin{listing}[H]
\begin{lstlisting}[language=HTML]
static-pages/
    index.html
    FAQ.md
\end{lstlisting}
\caption{Example static pages directory}
\label{lst:static-pages-dir-example}
\end{listing}

\begin{listing}[H]
\begin{lstlisting}[language=HTML]
<h1>
    MyLibrary reference documentation
</h1>
<div>
    This page contains the reference documentation of MyLibrary.
</div>
\end{lstlisting}
\caption{Example static page in HTML}
\label{lst:example-static-page1}
\end{listing}

\begin{listing}[H]
\begin{lstlisting}[language=HTML]

Run `dotnet add package MyLibrary.dll`.
\end{lstlisting}
\caption{Example static page in Markdown}
\label{lst:example-static-page2}
\end{listing}

In addition to pages, we may also include custom JavaScript files, images, or any other resources in the static pages directory, and then reference them from the pages.
It is also possible to provide custom CSS styles; however, they must be placed in the \texttt{css/styles.css} file.
In this case, we do not need to reference the CSS file manually, as it is included automatically.
However, it is important to keep in mind that the template styles are applied to the static pages as well.
Therefore, we should use custom styles only for minor improvements, rather than completely changing the overall appearance of the page.

\subsection{Documentation versioning}
\label{sec:user-docs-versions}

We can optionally make the documentation versioned.
This means the documentation consists of multiple versions, which can be switched between.
For instance, we can create version \texttt{v1.0} of the documentation, using the \texttt{--doc-version} option, that corresponds to version \texttt{1.0} of a library.
Then, when version \texttt{1.1} of the library is published, we can add a new documentation version, as
displayed in Listing~\ref{lst:user-docs-versions1}.
Naturally, it is mandatory to specify the same output directory.

\begin{listing}[H]
\begin{lstlisting}[language=bash]
refdocgen MyLibrary.dll --doc-version v1.0

# after version 1.1 is published
refdocgen MyLibrary.dll --doc-version v1.1
\end{lstlisting}
\caption{Creating various versions of the documentation}
\label{lst:user-docs-versions1}
\end{listing}

The documentation versions do not necessarily have to correspond to the library versions.
For instance, we may create two documentation versions, one showing the public API, and the other including even private members, as displayed in Listing~\ref{lst:user-docs-versions2}.

\begin{listing}[H]
\begin{lstlisting}[language=bash]
refdocgen MyLibrary.dll --doc-version v1.0-public
refdocgen MyLibrary.dll --doc-version v1.0-private 
    --min-visibility Private
\end{lstlisting}
\caption{Creating both public and private API of a library}
\label{lst:user-docs-versions2}
\end{listing}

\subsection{YAML configuration}
\label{sec:user-docs-yaml}

Instead of using command line arguments, it is possible to use a YAML file for configuration.
The main advantage is that the configuration does not have to be repeated each time and can be easily shared.
The YAML file can either be generated automatically (when using the \texttt{--save-config} flag) or created manually.
Although not mandatory, it is recommended to use the \texttt{refdocgen.yaml} filename.
The structure of YAML and command line configuration is very similar, as the keys in the YAML file correspond to the command-line options, while:

\begin{itemize}
    \item The \texttt{input} key, which is the only mandatory argument, corresponds to the \texttt{INPUT} command line argument.
    \item All the other keys have the same name as the matching command line option (without the starting dashes). For instance, the \texttt{output-dir} key corresponds to the \texttt{--output-dir} option. 
    It is not possible to use the short option names in YAML.
    \item The \texttt{save-config} option is not supported, as it does not make sense here.
    \item The default values are the same as in the command line configuration.
\end{itemize}

Listing~\ref{lst:cmd-save-config} shows an example command line configuration with the \texttt{--save-config} option, which results in the creation of the \texttt{refdocgen.yaml} file displayed in Listing~\ref{lst:cmd-line-yaml}.
The next time we want to use the same configuration, we do not need to repeat the individual options; instead, we can just run \texttt{refdocgen refdocgen.yaml} and the configuration will be loaded from the YAML.

\begin{listing}[H]
\begin{lstlisting}[language=bash]
refdocgen MyLibrary.sln 
    -o custom-folder
    --verbose 
    --force-create 
    --min-visibility Private 
    --exclude-projects MyLibrary.Tests 
    --exclude-namespaces MyLibrary.Internal MyLibrary.Experimental 
    --save-config
\end{lstlisting}
\caption{Example command line configuration}
\label{lst:cmd-save-config}
\end{listing}

\begin{listing}[H]
\begin{lstlisting}[language=bash]
input: MyLibrary.sln
output-dir: custom-folder
template: Default
verbose: true
force-create: true
min-visibility: Private
inherit-members: NonObject
exclude-projects:
  - MyLibrary.Tests
exclude-namespaces:
  - MyLibrary.Internal
  - MyLibrary.Experimental
\end{lstlisting}
\caption{Example YAML configuration file}
\label{lst:cmd-line-yaml}
\end{listing}

\subsection*{Error reporting}

If the configuration is invalid or the documentation generation fails, a descriptive error message is displayed.
For instance, if the provided DLL cannot be found, the following error message is printed: \texttt{The assembly at path 'PATH' was not found}.
When using the \texttt{--verbose} flag, additional details about the error (such as the stack trace) are displayed.

\subsection*{Supported modifiers}

Generally, most of the type, member, and parameter modifiers in C\# are recognized by \textit{RefDocGen}.
However, selected modifiers are not supported and thus do not appear in the generated documentation, but these are typically implementation details that do not affect the API.
Specifically, the following modifiers are not supported:
\texttt{extern}, \texttt{file}, \texttt{managed}, \texttt{partial}, \texttt{record}, \texttt{scoped}, \texttt{unmanaged}, \texttt{unsafe}, and \texttt{volatile}.
Likewise, the following type parameter constraints are not currently supported:
\texttt{notnull}, \texttt{unmanaged}, \texttt{default}, and \texttt{allows ref struct}.
