\chapter{Introduction}

Reference documentation is widely used in software development to document project APIs, making the development process much easier.
It provides an overview of the types and members declared in the project, along with their documentation comments.
Reference documentation is typically generated by a program called a reference documentation generator (or simply a documentation generator).
Some programming languages include a standard reference documentation generator as part of their SDK (such as \texttt{Javadoc} for Java). 
In other languages, there's a well-established third-party generator, e.g. \texttt{Sphinx} for Python.
However, in .NET, the situation is quite different.
There are multiple generators available, including \texttt{DocFX}, \texttt{Doxygen}, and \texttt{SHFB}, each having its advantages and limitations, 
such as the need for extensive configuration or platform dependency.
This brings us to the primary goal of the thesis -- to develop a reference documentation generator for .NET.
The goals will be discussed in more detail in the following chapters.

\section{Context}

Before proceeding to the goals of the thesis, it's important to describe the use cases of reference documentation and the broader context.

The reference documentation is primarily used by two groups of people.
\begin{itemize}
    \item \textbf{Developers using the library} access the reference documentation to view the library's documented API. 
    Typically, only publicly visible types and members are included. 
    Users typically reach the reference documentation via links from the user documentation.
    \item \textbf{Developers maintaining the library} may also use the reference documentation, although this use case is slightly less common.
    Here, the primary goal of the documentation is to help the programmers understand the project's internal structure. 
    It is very beneficial during the process of onboarding new team members. 
    In this case, the documentation often includes non-public members as well.
\end{itemize}

The documentation may be created in many formats, such as HTML, Markdown, or LaTeX, with HTML being the most common.
It displays the documentation comments contained in the code, along with the type and member data, that the generator extracts from the source or intermediate code.

Figure~\ref{fig:ref-doc-example} shows an example reference documentation for the \texttt{User} class generated by \texttt{Doxygen}.
Notice that there's a dedicated page for the type containing its documentation \textit{(A)} as well as the list of the declared members with the corresponding documentation comments \textit{(B)}. 
There is also a menu with the search bar at the top of the page \textit{(C)}.
The same observations apply to the vast majority of reference documentation pages, regardless of the generator.

Reference documentation is often accompanied by user documentation, which typically consists of text and code snippets.
The user documentation can be written in HTML; however, there's a much easier way to do it -- using a static site generator (SSG).
SSGs, such as Jekyll or MkDocs, are programs 
that use text written in a markup language (often Markdown) to create static web pages.
% SSGs enable us to focus only on the textual content of the documentation, and no HTML or CSS knowledge is required, which is a great advantage.
When building the documentation, we typically just select one of the provided HTML templates to create the webpage.

Many reference documentation generators, for instance, DocFX have at least some of the capabilities of SSGs. 
On the other hand, it is also possible to use 
the reference documentation generator solely for the reference docs and
create the user documentation using SSG.

\section{Goals}

Now, we have a basic knowledge of the context and we'll continue with the goals of our program.

First of all, many generators, including Doxygen and DocFX, require a non-trivial setup.
While the extensive configuration may seem like a benefit, a non-trivial amount of time is required to become familiar with the tools.
In many cases, especially in the case of smaller libraries, this leads to the harsh reality that the creator  
decides not to generate the reference documentation because he doesn't have the time (or will) to study the configuration. 
So, our documentation generator should be easy to use.
In other words, simply running the generator from the command line and specifying the input should be enough.
Note that there should definitely be support for a configuration file, so we don't have to repeat the same configuration over and over.
However, the default options should be reasonable and applicable to most cases.
Thus, we can formulate our first goal:

\begin{itemize}
    \item \label{G1} G1: Zero configuration build
\end{itemize}

Another observation is that the user may not want to use any of the built-in templates, instead they prefer to use the one provided by the community or even create a custom one.
The reason may be a different design or color palette that better corresponds to the project.
This also allows the users to create and share their templates.

\begin{itemize}
    \item G2: Support for custom templates
\end{itemize}

As mentioned before, it's often beneficial to have user documentation along the reference one. 
Our program should definitely not have all the features of an SSG, nevertheless, there should be at least basic support for static content (such as custom HTML pages), which gives us another goal.

\begin{itemize}
    \item G3: Support for custom static content 
\end{itemize}

The API typically evolves over time, however not all users use the most recent version of the program.
As a consequence, we typically want to maintain multiple versions of the documentation (each corresponding to the versions of our library) at once.

\begin{itemize}
    \item G4: Support for documentation versioning
\end{itemize}

We also should keep in mind that the program may be written in any .NET language. 
Even though C\# is the most commonly used, other .NET languages, such as F\# are also used in some cases.
We don't want to exclude those libraries, so that leads us to another goal.

\begin{itemize}
    \item G2: Support for multiple .NET languages
\end{itemize}


Last but not least, we also want to follow the recent trends and provide a modern visually appealing user interface.
As we've seen in Figure~\ref{fig:ref-doc-example}, the default UI of Doxygen is quite obsolete,
so this requirement is not something that could be assumed automatically.
So, our last goal is

\begin{itemize}
    \item G6: Modern UI
\end{itemize}

In the following chapters, we will analyze the problem more in detail.
