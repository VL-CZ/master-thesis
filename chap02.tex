\chapter{Analysis}
In the previous chapter, we outlined the key goals of this thesis, focusing on developing a reference documentation generator. 
To fulfill the goals, we must first address the fundamental challenges associated with generating documentation for .NET applications.

\section{XML documentation comments}

Firstly, it is worth noting that all major .NET languages use structured XML comments, well known from C\#, to document types and type members.
Interestingly, the set of XML documentation tags is not explicitly defined.
Instead, the official documentation~\cite{csharp_xml_docs} provides a set of recommended tags.
As a result, any XML tag is valid and can be used in the documentation comments 
(although in this case, it may not be correctly interpreted).

An example of a C\# method with XML documentation is shown in Program~\ref{lst:ex-cs-xml}; 
notice that both parameters and the return value are documented as well (using the \texttt{param} and \texttt{returns} tags, respectively).
Program~\ref{lst:ex-vb-xml} displays an analogous method in VB.NET.
We can see that VB.NET uses a different symbol for denoting documentation comments: triple single-quote mark.
However, the format of the comments remains the same, which is crucial, because the comments can be processed similarly, regardless of the language.

On the other hand, the documentation comments lack the context, such as:
\begin{itemize}
    \item the method name
    \item return value
    \item parameter types
    \item modifiers (\texttt{public}, \texttt{static}, etc.)
\end{itemize}

As shown in Program~\ref{lst:ex-cs-xml}, none of this information is present in the XML, even though it is essential for the reference documentation.
Thus, we can conclude that the documentation comments alone are insufficient for creating the reference docs.

\section{Extracting the context}

As discussed in the previous section, we need to obtain the definitions of types, members, and other code-related information (modifiers, attributes, etc.).
A straightforward technique applicable to any programming language is to parse the source code and extract the relevant information.

\subsection*{Using a custom language parser}

One way to achieve the parsing is by creating and using a custom language parser, which is the approach used by e.g. \texttt{Doxygen}. 
Although creating a language parser is often seen as a complex task, it could be partially simplified for our purposes, because we can skip the method bodies and parse solely the signatures.
However, there are also numerous other challenges related to this approach.

We will illustrate the first one using a simple example. Consider a method that returns an instance of \texttt{Point} class.
The parser can recognize the name of the return type, but it is not easy to discover any other information about the type, such as its namespace.
This is a problem, because in the reference documentation, we typically want to uniquely identify the type by providing a link to its definition or showing its fully qualified name, so the type name alone is insufficient.
Moreover, multiple types with the same name may be declared in different namespaces.

One possible solution would be to browse all files within the namespaces used by the current file and search for the given type.
Nevertheless, this technique fails if the type is declared in an external library, as the source code is not part of the library distribution.

It is worth noting that a similar issue applies to, for instance, base types. 
Without properly resolving the base type, it becomes difficult to obtain the inherited members, and therefore they cannot be included in the resulting documentation.

Another drawback is that a custom parser is not fully language-independent, because each language has a different syntax. 
Therefore, to satisfy the requirement R5, we would need either a separate parser for each language or a shared one capable of handling all languages.
However, this would significantly complicate the process, since we would need to resolve many edge cases for each language.
Furthermore, such a parser would need updates for every new language feature, which also adds a bit of complexity.

\subsection*{Using an existing parser}

Another, much simpler option is to use an existing language parser, as \texttt{DocFX} does internally. 
The most popular tool for this purpose is the C\# compiler, \texttt{Roslyn}, which, among its other capabilities, can parse the source code.
With Roslyn, we can easily inspect the syntax tree and perform semantic analysis using the semantic model, as described in the documentation~\cite{roslyn}.
This way, we can easily obtain all types, type members, and all relevant data.
The semantic model is essential because it resolves the issues with type identification discussed in the previous chapter.
Furthermore, the API of the semantic model is quite easy to use; for instance, a method is represented by the \texttt{IMethodSymbol} interface, which provides access to various data concerning the method.
For example, if we want to check whether a method is static, we can simply use the \texttt{IMethodSymbol.IsStatic} property. 
The interface also offers many other properties and methods; notably, there is a method for retrieving the corresponding documentation comment.

The disadvantage of \texttt{Roslyn} is that it is limited only to 2 languages: C\# and VB.NET.
There is an analogous library for parsing \texttt{F\#} code: \texttt{FSharp.Compi\-ler.Service}~\cite{fsharp_compiler_service}; 
however, it has a fundamentally different API, designed for F\# usage.
The main difference is that since F\# is primarily a functional programming language, the API heavily uses functional constructs, which makes its usage from C\# quite inconvenient.
Moreover, the objects representing F\# types and members are completely unrelated to the ones used by \texttt{Roslyn}, i.e. they do not share any common superclasses (except \texttt{object}) or interfaces.
As a result, integrating these two libraries would be complicated, as we would probably end up with two completely separate codebases: one using \texttt{Roslyn} and one using \texttt{FSharp.Compiler.Service}.

\subsection*{Using an assembly as the input}

Fortunately, the context information necessary for reference documentation is also contained within an assembly. 
This brings us to the idea of creating a generator that uses the assembly as its input and extracts the relevant data using reflection.
The key advantage of such generators, like \texttt{SHFB}, is that they are naturally language-independent, meaning they automatically satisfy the requirement R5.
Before we dive into further details, we need to explain the compilation process in more depth.

\section{Compilation process in .NET}

As stated in the .NET documentation~\cite{dotnet_execution_model} and illustrated in Figure~\ref{fig:net_compilation}, the compilation translates the source code of the program 
into the common intermediate language (CIL), which is a CPU-independent set of instructions that can be efficiently converted to native code. 
During program execution, CIL is converted to CPU-specific code, typically by a just-in-time (JIT) compiler.

In addition to CIL, the compiler also produces metadata, which describes the types in the code, including the definition of each type, the signatures of its members, and other data that the runtime uses at execution time, according to~\cite{dotnet_execution_model}.
The CIL and metadata are contained in a .NET assembly, which is typically stored as a dynamic link library (\texttt{.dll}).

\section{XML documentation file}

One important observation is that the documentation comments are not part of the assembly.
Instead, the compiler can optionally create an XML file containing the documentation of the declared types and their members, 
which is typically done by setting the \texttt{GenerateDocumentationFile} or \texttt{DocumentationFile} 
option, as mentioned in the MSBuild documentation~\cite{msbuild_docs}.
Program~\ref{lst:ex-xml-output} shows the resulting XML file containing the documentation of the method shown in Program~\ref{lst:ex-cs-xml}.
As we can see, the comments are stored inside a \texttt{member} element, which has a \texttt{name} attribute that uniquely identifies the corresponding type or type member.
The value of the \texttt{name} attribute is prefixed with an \textit{M} and a colon, which indicates that the documentation belongs to a method.

\begin{listing}[H]
\begin{lstlisting}[language=XML]
<?xml version="1.0"?>
<doc>
    <assembly>
        <name>MyApp</name>
    </assembly>
    <members>
        <member name="M:MyApp.MyClass.CalculateRectangleArea
                            (System.Double,System.Double)">
            <summary>
                Calculates the area of a rectangle given 
                its width and height.
            </summary>
            <param name="width">
                Width of the rectangle.
            </param>
            <param name="height">
                Height of the rectangle.
            </param>
            <returns> 
                The area of the rectangle.
            </returns>
        </member>
        ...
    </members>
</doc>
\end{lstlisting}

\label{lst:ex-xml-output}
\end{listing}

\section*{Evaluation of approaches}

In the previous sections, we have explained why creating a custom language parser or using an existing one may not be ideal.

On the other hand, using assembly as an input seems to be a reasonable choice.
Additionally, the development of such a generator is quite straightforward; we just need to extract the relevant data from the assembly metadata and combine it with the documentation comments retrieved from the XML documentation file.
However, this approach also has a downside: the need for program compilation, i.e., the project must be built before the documentation is generated.
Fortunately, this is not a limiting factor, since compiling the program is a routine task.

It is crucial to mention that all the information relevant to the reference documentation about types and members can be retrieved from the metadata. 
For instance, the object representing a method (i.e. \texttt{MethodInfo}) contains properties such as \texttt{IsStatic}, \texttt{IsPublic}, etc.
Naturally, this also makes sense, because .NET package distributions contain assemblies, rather than source code.
For example, when a method from a library is called, the caller simply needs to know whether it is, e.g., static, to call it correctly.
In general, any information that affects the caller must be stored somewhere in the assembly, or it can be inferred.
Some constructs may be purely language features and cannot be deduced from the assembly; however, these are only implementation details.
Therefore, such data are irrelevant to the reference documentation because they do not have any impact on the caller.

In conclusion, we can refine our objective -- to develop a reference
documentation generator for .NET that uses assembly as its input.

\section{XML documentation tags}

As mentioned earlier, the set of XML documentation tags is not explicitly defined. 
Instead, the recommended tags are typically described in the documentation of each .NET language.
It is also important to keep in mind that aside from the recommended tags, any XML tag is valid; in this case, it is simply copied to the XML documentation file.

The recommended tags slightly differ for each language, however, they can be classified into two categories, based on their usage.

\subsection{Top-level tags}

Top-level tags are present directly at the type or member definition, meaning they are not contained inside another tag.

The most common tag is \texttt{summary}, which describes a type or member, as previously shown in Program~\ref{lst:ex-cs-xml}. 
However, there are numerous other commonly used top-level tags, as shown in Table~\ref{table:top-level-tags}.

\begin{table}[h]
\centering
\begin{tabular}{|p{6cm}|p{6cm}|}
\hline
\textbf{Tag} & \textbf{Description} \\
\hline
\texttt{<summary>} & Describes a type or member. \\
\hline
\texttt{<remarks>} & Provides additional information about a type or member. \\
\hline
\texttt{<param name="...">} & Documents a parameter, identified by the \texttt{name} attribute \\
\hline
\texttt{<typeparam name="...">} & Documents a type parameter, identified by the \texttt{name} attribute. \\
\hline
\texttt{<returns>} & Documents a return value. \\
\hline
\texttt{<value>} & Documents a property value. \\
\hline
\texttt{<exception cref="...">} & Specifies and describes an exception that may be thrown. \\
\hline
\texttt{<seealso cref="..." /> } & Specifies a link to a related type or member. \\
\hline
\texttt{<seealso href="...">} & Specifies a link to a related URL, identified by the \texttt{href} attribute. \\
\hline
\end{tabular}
\caption{Top-level XML tags}
\label{table:top-level-tags}
\end{table}

The documentation is then stored inside those elements.
The only exception is the \texttt{<seealso cref="..." /> } tag, which is unpaired and thus does not have any content.

Additionally, several tags, notably \texttt{<param>}, \texttt{<typeparam>}, \texttt{<exception>}, and \texttt{<seealso>} may be present multiple times in the definition.
For instance, if a method has 3 parameters, there could be up to 3 \texttt{<param>} tags (one for each parameter).

\subsubsection*{Cref attribute}
As shown in Table~\ref{table:top-level-tags}, several tags have a \texttt{cref} attribute.
This attribute specifies that the tag references a code element, i.e., a type or a member. 

For instance, if there is a method somehow related to \texttt{Console.WriteLine}, we can include the following tag in its documentation: \texttt{<seealso cref="Console.WriteLine" />}.
The link to the \texttt{Console.WriteLine} should then be displayed in the resulting documentation of the given method.

However, in the XML documentation file, the attribute value is stored in a slightly different format.
The reason behind this is ambiguity, because there may be other \texttt{Console.WriteLine} method in a different namespace.
Thus, the compiler resolves the type or member and replaces it with its fully qualified name, prefixed by its kind.
In our case, the result would be 
\texttt{<seealso cref="M:System.Console.WriteLine" />} (\textit{M} denotes a method).
The whole format of the string is thoroughly described in the official documentation~\cite{csharp_xml_docs}.

\subsubsection*{Usage}

The \texttt{<summary>}, \texttt{<remarks>}, and \texttt{<seealso>} tags can be applied to any type or member.
The other top-level tags are typically intended only for a selection of types or members, as shown in Table~\ref{table:top-level-tags-usage}.

\hline
\texttt{<typeparam name="...">} & Generic types and methods \\
\hline
\texttt{<returns>} & Methods \\
\hline

\subsection{Reusing the documentation}

There are two more commonly used tags -- \texttt{<include>} and \texttt{<inheritdoc>}, both top-level and unpaired.

The \texttt{<include>} tag allows us to import the documentation from an external XML file by specifying the file path and the path to the element to include.
Note that this tag is unsupported in some languages, such as F\#.
When creating the XML documentation file, the compiler replaces the \texttt{<include>} tags with the actual documentation.
Thus, the \texttt{<include>} elements are not present in the resulting documentation file, meaning that we do not need to process them in any way.

The \texttt{inheritdoc} tag can be applied to any type and member and allows users to inherit the 
When applied to a type, the documentation is inherited from the base type or an implemented interface.
The official documentation~\cite{csharp_xml_docs} does not specify what happens if, e.g., both the base type and implemented interface are documented.
When the \texttt{inheritdoc} is applied to a member, the documentation is taken from the base definition of the member.
This means the identical member in the base type or an implemented interface.
Again, the documentation does not specify any precedence.

The \texttt{<inheritdoc>} supports 2 optional arguments: \texttt{cref} and \texttt{path}.

\begin{itemize}
    \item The \texttt{cref} attribute explicitly specifies the type or member from which the documentation is inherited.
    This is handy, for instance, if we have two equivalent methods -- one synchronous and the other asynchronous.
    In this case, we can avoid repeating the documentation by using \texttt{<inheritdoc>} with the \texttt{cref} attribute.
    \item The \texttt{path} attribute allows us to inherit only selected XML nodes, which is configured by providing an XPath query.
    Then, only the matching nodes are inherited; in other words, we may specify to inherit only the \texttt{summary} tag.
\end{itemize}

Unlike the \texttt{<include>} element, the \texttt{<inheritdoc>} is not resolved by a compiler.
In other words, the inheritdoc tags are still present in the resulting XML file.
As a result, the documentation inheritance must be handled by the documentation generator.

\section{Further requirement analysis}

In this section, we will analyze the requirements R1-R7, outlined in the first chapter, in more detail.

As discussed earlier, the requirement R1 states that the generator should be easy 
to use, as the only mandatory argument should be the input.
On the other hand, the generator naturally should also offer several optional arguments, such as the output folder.
However, these options should have reasonable default values.

\subsection*{Configuration using a file}

Next, consider a scenario in which a user generates the documentation using a custom configuration, then updates the code and wants to regenerate the documentation.
Instead of specifying all the options again, saving the configuration in a file would be much more convenient.
This also makes it easier to share configurations with other developers.

\subsection*{Option format}

Various file formats are used for configuration.
The easiest solution would be to store the options in the same format as on the command line, 
allowing users to copy the configuration into a file. 
However, this approach brings multiple drawbacks.
First, this file format is not standardized or widely recognized, so the text editor would not be capable of any text highlighting.
Another disadvantage, stemming from the lack of standardization, is that there is no easy way to recognize comments in the file.
Furthermore, we cannot use the command-line symbol for denoting comments, as it differs between various shells, which would cause inconsistency.
It is important to note that adding comments is a useful feature of the configuration file, because it is often beneficial to explain the rationale behind setting a certain option to a specific value.
In conclusion, the command line option format does not seem ideal.

\subsection*{Well known format}

The alternative way is to use a widely recognized configuration format, such as TOML, XML, JSON, or YAML. 
Using this approach, the disadvantages outlined above are typically resolved.
On the other hand, we lose the ability to simply copy-paste the options from the command line, although the conversion to the given format should not be complicated.

One option is to use a key-value configuration format, such as \textit{.ini} file, as the configuration is not expected to have a hierarchical structure.
While the \textit{.ini} format is not fully standardized, the \textit{TOML} format has a formal specification and is almost identical in structure.
However, the main downside of those formats is that they are not as widely adopted, especially compared to  XML, JSON, and YAML.
This is a disadvantage, as we should strive to use a format understood by a large share of users.

Another option is to use XML for configuration. While it is a powerful format, it often tends to be verbose, which makes it less ideal for our purposes.
JSON and YAML seem to be the most popular today.
Additionally, it seems to be losing popularity nowadays, in favor of JSON and YAML.
Compared to XML, JSON is more compact; however, its formal specification does not support comments, which is a considerable disadvantage.
Finally, YAML checks all boxes: it is widely recognized, supports comments, and has an even more compact syntax than JSON, which makes it an ideal choice. 
Based on the insights above, we can introduce two sub-requirements of requirement R1:

\begin{itemize}
    \item R1.1: Provide reasonable default values for command line arguments.
    \item R1.2: Support configuration using a YAML file.
\end{itemize}

Next, the generator should be designed to be extensible, as described in the requirement R2.
The documentation pages will naturally be generated from templates, written in an unspecified templating language, which get populated with data while the documentation is generated.

Firstly, it should be easily possible to use the same template system as the default UI.
If the user wanted to generate the documentation using the template system and data, it should be sufficient to provide the equivalent templates.
In other words, if the generator had 2 templates representing type and namespace pages, providing a custom version of those two should be sufficient.

Furthermore, the users should be able to write their own templates using a template engine of their choice. 
using the provided data representing the types and members.
In addition to templates themselves, the users should also provide a code that generates them.
In practice, this should be done by implementing a corresponding interface.

\begin{itemize}
    \item R2.1: Support for custom templates written in the same template language as the default UI.
    \item R2.2: The generator should allow users to use templates written in a templating language of their choice, accompanied by the code that generates them.
\end{itemize}

The requirement R3 mentions support for user-specified static pages.
As discussed before, the goal is not to create a full-fledged SSG; instead, a convention-based approach with no configuration is preferred.

A simple yet effective approach would be to give the user an option to include a folder containing static pages.
The generator should then recursively copy the files in the folder into the output directory, thus including the pages in the documentation.
Also, note that the relative paths between files stay the same because the directory structure is preserved.
As a result, the links between files can stay intact, which is a huge advantage of this approach.

When it comes to pages, we must consider several formats that users may want to use.
The natural option is to use HTML, as the resulting page will be in HTML format.
Moreover, we also want to support Markdown, since it is extremely popular these days and easy to write.
In addition to pages, the folder may contain other non-page files, such as CSS, JavaScript, or images, so we need to handle those as well.
As a result, we can further clarify requirement R3:

\begin{itemize}
    \item R3.1: Provide an option to add a folder containing static files to be included in the documentation. 
    \item R3.2: Support static pages in both HTML and Markdown format.
\end{itemize}

The requirement R4 focuses on documentation versioning.
The generator should support an option (both on the command line and in the configuration file) for creating a specific version of the documentation, e.g. \texttt{v1.2}. 
The resulting documentation should then be stored not in the output folder, but in its subfolder identified by the version number (\texttt{v1.2} in our case).
This way, the output folder may contain multiple versions of the documentation.

Additionally, the default UI should allow users to switch between different versions.
To achieve this, the UI should include a dropdown menu showing the available versions.
Whenever a new version of the documentation is generated, all the older versions should be updated to include the most recent version in the dropdown.
Thus, we can define two sub-requirements:

\begin{itemize}
    \item R4.1: Option to create a specific version of the documentation.
    \item R4.2: Dropdown menu for version selection in the UI.
\end{itemize}

We have skipped requirements R5, R6, and R7, as they remain unchanged.
Furthermore, since we have decided to extract the context data from an assembly, requirement R5 is automatically satisfied, as discussed earlier.

First and foremost, it is essential to have an index page showing all namespaces contained in an assembly, and the types declared inside them.
Thus, our eighth requirement is:

\begin{itemize}

        \item[•] R8.1: Show list of namespaces.
        \item[•] R8.2: Show a list of types declared in each namespace.
    \end{itemize}

Furthermore, there should be a page for each namespace, displaying all of the types contained.
For each type, there should be a link to its definition and its documentation, which leads us to the following requirement:

\begin{itemize}
    \item R9: Separate page for each namespace.
    \begin{itemize}
        \item[•] R9.1: Display a list of types contained in the namespace.
    \end{itemize}
\end{itemize}

Finally, there should be a page for each type displaying its signature in C\# format and documentation.
The documentation should be divided into sections, corresponding to top-level XML tags.
In addition to that, there should be a section displaying the attributes applied to a type.
So, the documentation can contain those sections (the section should be displayed only if the corresponding tag is present):

\begin{itemize}
    \item[-] Summary (corresponding to the \texttt{<summary>} tag)
    \item[-] Remarks (corresponding to the \texttt{<remarks>} tag)
    \item[-] Type parameters (corresponding to the \texttt{<typeparam>} tags)
    \item[-] See Also (corresponding to the \texttt{<seealso>} tags)
    \item[-] Attributes
\end{itemize}

Furthermore, below the type definition, there should be a list of declared members, grouped
into categories based on the member kind (field, property, method, etc.), similar to \texttt{SHFB}.
Each member should again display the signature and the documentation, again corresponding to the XML tags, along with the section displaying attributes.
So, potentially, the documentation can contain the following sections:

\begin{itemize}
    \item[-] Summary (corresponding to the \texttt{<summary>} tag)
    \item[-] Remarks (corresponding to the \texttt{<remarks>} tag)
    \item[-] See Also (corresponding to the \texttt{<seealso>} tags)
    \item[-] Type parameters (corresponding to the \texttt{<typeparam>} tags)
    \item[-] Returns (corresponding to the \texttt{<returns>} tag)
    \item[-] Param (corresponding to the \texttt{<param>} tag)
    \item[-] Value (corresponding to the \texttt{<value>} tag)
    \item[-] Attributes
\end{itemize}

This gives us another requirement:

\begin{itemize}
    \item R10: Separate page for each type
    \begin{itemize}
        \item[•] R10.1: Show type signature in C\# format.
        \item[•] R10.2: Show type documentation, divided into sections corresponding to XML tags.
        \item[•] R10.3: Show signatures of all members contained in the type.
        \item[•] R10.4: Show documentation of all members, divided into sections corresponding to XML tags.
    \end{itemize}
\end{itemize}

\section*{Other requirements}
In previous sections, we thoroughly described the requirements R1-R7 introduced in the first chapter. 
Next, we stated multiple other requirements based on the analysis of existing solutions and the official .NET documentation.
In this section, we will present the remaining requirements, based on various use cases.

The first important observation is that the program to be documented may consist of multiple assemblies. 
In this case, we typically want to include multiple assemblies in the documentation, which leads us to the following requirement:

\hfill

\textbf{\textcolor{blue}{R16: Option for selecting solution as the input.}}

\hfill

On the other hand, when generating a documentation for a solution, we typically do not want to include all projects contained in the solution; for instance, we often want to exclude the assemblies containing tests. 
Thus, there should be a way to exclude selected assemblies from the resulting documentation, which is our next requirement:

\begin{itemize}
    \item R17: Option to exclude selected assemblies.
\end{itemize}

Additionally, the assembly may contain certain types we would like to exclude from the documentation.
For instance, consider an app that includes Razor templates, which are represented as regular .NET classes.

One option would be to use custom XML tags (for instance \texttt{<ignore />}) and mark each type to be excluded from the documentation. 
However, this approach brings a significant disadvantage, as it creates a coupling between the program and the generator.
In other words, the program developers need to be aware of the documentation generator.

An alternative solution is to support an option that allows users to exclude types based on their namespaces, which completely removes the coupling. 
Thus, we can formulate the subsequent requirement:

\begin{itemize}
    \item R18: Option to exclude types in selected namespaces.
\end{itemize}

As discussed in section~\ref{section:context}, reference documentation is primarily intended for developers using a library or maintainers of the library.
In the first case, only the public API is relevant, so public members alone are enough, while in the second case, it is often beneficial to include private members as well.
This gives us another requirement:

\begin{itemize}
    \item R19: Option for selecting types and members based on their accessibility level.
\end{itemize}

It is also worth noting that users may want to exclude inherited members from the documentation, based on different use cases.
For instance, it may be preferred to exclude inherited members to focus solely on the specific API exposed by the types. 
As a result, we can formulate the following requirement:

\begin{itemize}
    \item R20: Option for including/excluding the inherited members.
\end{itemize}
