\chapter{Analysis}
In the previous chapter, we outlined the key goals of this thesis, focusing on developing a reference documentation generator. 
To fulfill the goals, we must first address the fundamental challenges associated with generating documentation for .NET applications.

\section{XML documentation comments}

Firstly, it is worth noting that all major .NET languages use structured XML comments, well known from C\#, to document types and type members.
Interestingly, the set of XML documentation tags is not explicitly defined.
Instead, the official documentation provides a set of recommended tags.
As a result, any XML tag is valid and can be used in the documentation comments
(although in this case, it may not be correctly interpreted).

An example of a C\# method with XML documentation is shown in Program~\ref{lst:ex-cs-xml}; 
notice that both parameters and the return value are documented as well (using the \texttt{param} and \texttt{returns} tags, respectively).
Program~\ref{lst:ex-vb-xml} displays an analogous method in VB .NET.
We can see that Visual Basic uses a different symbol for denoting documentation comments: triple single-quote mark.
However, the format of the comments remains the same, which is crucial.

We can conclude that the documentation comments alone are insufficient for the reference docs. 
This is because they lack context, such as the corresponding member signature, which should be displayed in the documentation.
For instance, note that the \texttt{param} element does not include any information about the parameter type.

Therefore, we need to obtain the definitions of types, members, and other code-related information. 
A straightforward approach applicable to any programming language is to parse the source code and extract the relevant information.
One way to achieve this is by creating and using a custom parser, which is the approach used by e.g. \texttt{Doxygen}. 
However, there is a major disadvantage -- complexity, since creating a language parser is a very complex task.
Another, much easier, option is to use an existing parser, for instance \texttt{Roslyn}, which is what \texttt{DocFX} does internally. 
Roslyn allows us to inspect the syntax tree and thus obtain the member signatures as well as to perform semantic analysis using the Semantic model.
This way, we can easily obtain all members of a type and any data concerning it.

The disadvantage of \texttt{Roslyn} is that it is limited only to 2 languages: C\# and Visual Basic .NET.
There's an analogous library for \texttt{F\#}: \texttt{FSharp.Compiler.Service}, however, it has a different API, so integrating those 2 parsers would further complicate the process. 

Since .NET is a managed environment, there is another way to develop a reference documentation generator, completely independent of the programming language: by extracting the data from an assembly. 
Before we dive into further details, we need to explain the compilation process in more depth.

\section{Compilation process in .NET}

As stated in the .NET documentation~\cite{dotnet_execution_model} and illustrated in Figure~\ref{fig:net_compilation}, the compilation translates the source code of the program 
into the common intermediate language (CIL), which is a CPU-independent set of instructions that can be efficiently converted to native code. 
CIL includes instructions for loading, storing, initializing, and calling methods on objects, as well as instructions for arithmetic and logical operations, control flow, and other operations.
During program execution, CIL is converted to CPU-specific code, typically by a just-in-time (JIT) compiler.

In addition to CIL, the compiler also produces metadata, which describes the types in the code, including the definition of each type, the signatures of its members, and other data that the runtime uses at execution time, according to~\cite{dotnet_execution_model}.
The CIL and metadata are contained in a .NET assembly, which is typically stored as a dynamic link library (\texttt{.dll}).

One important observation is that the documentation comments are not part of the assembly.
Instead, the compiler can optionally create an XML file containing the documentation of the declared types and their members, 
which is typically done by setting the \texttt{GenerateDocumentationFile} or \texttt{DocumentationFile} 
option, as mentioned in the MSBuild documentation~\cite{msbuild_docs}.
Program~\ref{lst:ex-xml-output} shows the resulting XML file containing the documentation of the method shown in Program~\ref{lst:ex-cs-xml}.
As we can see, the comments are stored inside a \texttt{member} element, which has a \texttt{name} attribute that uniquely identifies the corresponding type or type member.
The value of the \texttt{name} attribute is prefixed with an \textit{M} and a colon, which indicates that the documentation belongs to a method.

Using this knowledge, developing a generator that uses assembly as its input is quite straightforward; we just need to extract the relevant data from the assembly metadata and XML documentation file and combine it.
A nice property of such generators, like \texttt{SHFB}, is that they automatically satisfy R5.
On the other hand, the downside of this approach is the need for program compilation, i.e. the project must be built before the documentation is generated.
However, this is not a limiting factor for us.
Based on this, we can refine our objective -- to develop a reference
documentation generator for .NET that uses assembly as its input.

Since we have not explained it yet, we will briefly describe how to extract the type and member information from the assembly metadata.
This is done using reflection, which in general refers to the ability of a program to inspect or modify other code or itself.
Reflection allows us to load assemblies, obtain the declared types and type members and inspect their data.
An example usage of reflection is shown in Program~\ref{lst:ex-reflection}, which presents a code snippet that prints the return type and name of all methods contained in the \texttt{Person} type.
Notice that something similar, obviously much more complex, will be performed by our documentation generator.
The snippet may thus serve as a good starting point for the type and member data extraction.

\subsection{Doxygen}

Doxygen is a well-established documentation generator that supports many languages, including C++, C\#, Java, PHP, and Python.
It is a typical example of a generator parsing source code; 
interestingly, there is a shared parser for all languages implemented using \texttt{flex}.~\cite{doxygen_docs} 

Doxygen is highly configurable, offering more than 300 various options.

The configuration is stored as a collection of key-value pairs in a configuration file, typically called \texttt{Doxyfile}.
The downside of the extensive option support is the complexity of the configuration file,
which has by default over 2000 lines (most of the content consists of the individual option documentations, though).

The documentation is built by running \texttt{Doxygen} from the command line.
In addition to HTML, there are multiple output formats available, such as LaTeX and XML.
Doxygen can also be used for user documentation, as it allows us to include custom static pages from the provided files in \texttt{.dox}, \texttt{.txt}, or \texttt{.md} format.~\cite{doxygen_docs}

By default, the documentation may be created in a light or dark mode; however, Doxygen supports further customization at various levels.
It is possible to provide a custom stylesheet, page fragment, or the whole layout.
 
An example reference documentation generated by Doxygen is shown in Figures \ref{fig:doxygen1} and \ref{fig:doxygen2}. Notice that the default UI is unfortunately quite old-school.

\subsection{Sandcastle Help File Builder}

Sandcastle Help File Builder (SHFB) is another documentation generator for .NET.
It uses reflection to extract the data from the assembly.

The configuration is stored in a standard MSBuild-format project file.
This means that the documentation can be built using \texttt{dotnet build} or \texttt{msbuild} command.

SHFB supports several custom documentation tags, for instance \texttt{threadsafety} tag denoting the thread safety of the member.

There are several output formats available: HTML, Markdown, and Open XML document.
The default HTML template has a separate page for each member.

\subsection{JavaDoc}

Javadoc is a documentation generator for Java; furthermore, it is even part of the JDK.

The javadoc command parses the declarations and documentation comments in a set of Java source files and produces a corresponding set of HTML pages that describe (by default) the public and protected classes,

Can be run from command line.

Super easy to use - no configuration. 
However, configuration is possible using project file.

By default, it supports only HTML output, others can be achieved using (or writing own) extensions.

\subsection{Sphinx}

Sphinx is a documentation generator or a tool that translates a set of plain text source files into various output formats, automatically producing cross-references, indices, etc. That is, if you have a directory containing a bunch of reStructuredText or Markdown documents, Sphinx can generate a series of HTML files, a PDF file (via LaTeX), man pages and much more.

Sphinx focuses on documentation, in particular handwritten documentation, however, Sphinx can also be used to generate blogs, homepages and even books. Much of Sphinx’s power comes from the richness of its default plain-text markup format, reStructuredText, along with its significant extensibility capabilities.

Quite complex configration options, many files.

Originally for Python, but includes support for other languages such as JavaScript and C++.

Many built in themes, rtd is quite popular.
