\chapter{Analysis}
\label{ch:second}

In the previous chapter, we outlined the key goals of this thesis, focusing on developing a reference documentation generator. 
To fulfill the goals, we must first address the fundamental challenges associated with generating documentation for .NET applications.

\section{XML documentation comments}

Firstly, it is worth noting that all major .NET languages use structured XML comments, well known from C\#, to document types and type members.
Interestingly, the set of XML documentation tags is not explicitly defined.
Instead, the official documentation~\cite{csharp_xml_docs} provides a set of recommended tags.
As a result, any XML tag is valid and can be used in the documentation comments 
(although in this case, it may not be correctly interpreted).

An example of a C\# method with XML documentation is shown in Listing~\ref{lst:ex-cs-xml}; 
we can notice that both parameters and the return value are documented as well (using the \texttt{param} and \texttt{returns} tags, respectively).
Listing~\ref{lst:ex-vb-xml} displays an analogous method in VB.NET.
We can see that VB.NET uses a different symbol for denoting documentation comments: a triple single-quote mark.
However, the format of the comments remains the same, which is crucial because the comments can be processed similarly, regardless of the language.

On the other hand, the documentation comments lack the context, such as:
\begin{itemize}
    \item the method name
    \item return value
    \item parameter types
    \item modifiers (\texttt{public}, \texttt{static}, etc.)
\end{itemize}

As shown in Listing~\ref{lst:ex-cs-xml}, none of this information is present in the XML, even though it is essential for the reference documentation.
Thus, we can conclude that the documentation comments alone are insufficient for creating the reference docs. 

\begin{listing}
\begin{lstlisting}
/// <summary>
/// Calculates the area of a rectangle given its width and height.
/// </summary>
/// <param name="width">Width of the rectangle.</param>
/// <param name="height">Height of the rectangle.</param>
/// <returns>The area of the rectangle.</returns>
public static double CalculateRectangleArea(
    double width, double height)
{
    return width * height;
}

\section{Extracting the context}

As discussed in the previous section, we need to obtain the definitions of types, members, and other code-related information (modifiers, attributes, etc.).
A straightforward technique applicable to any programming language is to parse the source code and extract the relevant information.

\subsection*{Using a custom language parser}

One way to achieve the parsing is by creating and using a custom language parser, which is the approach used by e.g. \textit{Doxygen}. 
Although creating a language parser is often seen as a complex task, it could be partially simplified for our purposes because we can skip the method bodies and parse solely the signatures.
However, there are also numerous other challenges related to this approach.

We will illustrate the first one using a simple example. Consider a method that returns an instance of the \texttt{Point} class.
The parser can recognize the name of the return type, but it is not easy to discover any other information about the type, such as its namespace.
This is a problem because in the reference documentation, we typically want to uniquely identify the type by providing a link to its definition or showing its fully qualified name, so the type name alone is insufficient.
Moreover, multiple types with the same name may be declared in different namespaces.

One possible solution would be to browse all files within the namespaces used by the current file and search for the given type.
Nevertheless, this technique fails if the type is declared in an external library, as the source code is not part of the library distribution.
It is worth noting that a similar issue applies to, for instance, base types. 
Without properly resolving the base type, it becomes difficult to obtain the inherited members, and therefore, they cannot be included in the resulting documentation.

Another drawback is that a custom parser is not fully language-independent, because each language has a different syntax. 
Therefore, to satisfy Requirement~\ref{req:lang-ind}, we would need either a separate parser for each language or a shared one capable of handling all languages.
However, this would significantly complicate the process, since we would need to resolve many edge cases for each language.
Furthermore, such a parser would need updates for every new language feature, which also adds a bit of complexity.

\subsection*{Using an existing parser}

Another, much simpler option is to use an existing language parser, as \textit{DocFX} does internally. 
The most popular tool for this purpose is the C\# compiler, \textit{Roslyn}~\cite{roslyn}, which, among its other capabilities, can parse the source code.
With Roslyn, we can easily inspect the syntax tree and perform semantic analysis using the semantic model, as described in the documentation~\cite{roslyn}.
This way, we can easily obtain all types, type members, and other relevant data.
The semantic model is essential because it resolves the issues with type identification discussed in the previous chapter.
Furthermore, the API of the semantic model is quite easy to use; for instance, a method is represented by the \texttt{IMethodSymbol} interface, which provides access to various data concerning the method.
For example, if we want to check whether a method is static, we can simply use the \texttt{IMethodSymbol.IsStatic} property. 
The interface also offers many other properties and methods; notably, there is a method for retrieving the corresponding documentation comment.

The disadvantage of \textit{Roslyn} is that it is limited only to 2 languages: C\# and VB.NET.
There is an analogous library for parsing F\# code: \textit{FSharp.Compi\-ler.Service}~\cite{fsharp_compiler_service}; 
however, it has a fundamentally different API, designed for F\# usage.
The main difference is that since F\# is primarily a functional programming language, the API heavily uses functional constructs, which makes its usage from C\# quite inconvenient.
Moreover, the objects representing F\# types and members are completely unrelated to the ones used by \textit{Roslyn}, i.e., they do not share any common superclasses (except \texttt{object}) or interfaces.
As a result, integrating these two libraries would be complicated, as we would probably end up with two completely separate codebases: one using \textit{Roslyn} and one using \textit{FSharp.Compiler.Service}.

\subsection*{Using an assembly as the input}

Fortunately, the context information necessary for reference documentation is also contained within an assembly. 
This brings us to the idea of creating a generator that uses the assembly as its input and extracts the relevant data using reflection.
The key advantage of such generators, like \textit{SHFB}, is that they are naturally language-independent, meaning they automatically satisfy Requirement~\ref{req:lang-ind}.
Before we dive into further details, we need to explain the compilation process in more depth.

\section{Compilation process in .NET}

As stated in the .NET documentation~\cite{dotnet_execution_model} and illustrated in Figure~\ref{fig:net_compilation}, the compilation translates the source code of the program 
into the common intermediate language (CIL), which is a CPU-independent set of instructions. 
During program execution, CIL is converted to CPU-specific code, typically by a just-in-time (JIT) compiler.

In addition to CIL, the compiler also produces metadata, which describes the types in the code, including the definition of each type, the signatures of its members, and other data that the runtime uses at execution time, according to~\cite{dotnet_execution_model}.
The CIL and metadata are contained in a .NET assembly, which is typically stored as a dynamic link library (\textit{.dll}).

\section{XML documentation file}
\label{section:xml-doc}

One important observation is that the documentation comments are not part of the assembly.
Instead, the compiler can optionally create an XML file containing the documentation of the declared types and their members, 
which is typically done by setting the \texttt{GenerateDocumentationFile} or \texttt{DocumentationFile} 
option, as mentioned in the \textit{MSBuild} documentation~\cite{msbuild_docs}.
Listing~\ref{lst:ex-xml-output} shows the resulting XML file containing the documentation of the method shown in Listing~\ref{lst:ex-cs-xml}.
As we can see, the comments are stored inside a \texttt{member} element, which has a \texttt{name} attribute that uniquely identifies the corresponding type or type member.
The value of the \texttt{name} attribute is prefixed with an \textit{M} and a colon, which indicates that the documentation belongs to a method.

\begin{listing}[H]
\begin{lstlisting}[language=XML]
<?xml version="1.0"?>
<doc>
    <assembly>
        <name>MyApp</name>
    </assembly>
    <members>
        <member name="M:MyApp.MyClass.CalculateRectangleArea
                            (System.Double,System.Double)">
            <summary>
                Calculates the area of a rectangle given 
                its width and height.
            </summary>
            <param name="width">
                Width of the rectangle.
            </param>
            <param name="height">
                Height of the rectangle.
            </param>
            <returns> 
                The area of the rectangle.
            </returns>
        </member>
        ...
    </members>
</doc>
\end{lstlisting}
\caption{Example of the resulting XML documentation file}
\label{lst:ex-xml-output}
\end{listing}

\section*{Evaluation of approaches}

In the previous sections, we have explained why creating a custom language parser or using an existing one may not be ideal.
On the other hand, using assembly as an input seems to be a reasonable choice.
Additionally, the development of such a generator is quite straightforward; we just need to extract the relevant data from the assembly metadata and combine it with the documentation comments retrieved from the XML documentation file.
However, this approach also has a downside: the need for program compilation, i.e., the project must be built before the documentation is generated.
Fortunately, this is not a limiting factor, since compiling the program is a routine task.

It is crucial to mention that all the information relevant to the reference documentation about types and members can be retrieved from the metadata. 
For instance, the object representing a method (i.e. \texttt{MethodInfo}) contains properties such as \texttt{IsStatic}, \texttt{IsPublic}, etc.
Naturally, this also makes sense because .NET package distributions contain assemblies, rather than source code.
For example, when a method from a library is called, the caller simply needs to know whether it is, e.g., static, to call it correctly.
In general, any information that affects the caller must be stored somewhere in the assembly, or it can be inferred.
Some constructs may be purely language features and cannot be deduced from the assembly; however, these are only implementation details.
Therefore, such data is irrelevant to the reference documentation because they do not have any impact on the caller.

In conclusion, we can refine our objective -- to develop a reference
documentation generator for .NET that uses assembly as its input.

\section{XML documentation tags}

As mentioned earlier, the set of XML documentation tags is not explicitly defined. 
Instead, the recommended tags are typically described in the documentation of each .NET language.
It is also important to keep in mind that aside from the recommended tags, any XML tag is valid; in this case, it is simply copied to the XML documentation file.
The recommended tags slightly differ for each language; however, they can be classified into two categories, based on their usage.

\subsection{Top-level tags}

Top-level tags are present directly at the type or member definition, meaning they are not contained inside another tag.
The most common tag is \texttt{<summary>}, which describes a type or member, as previously illustrated in Listing~\ref{lst:ex-cs-xml}. 
However, there are numerous other commonly used top-level tags, as shown in Table~\ref{table:top-level-tags}.

\begin{table}[h]
\centering
\begin{tabular}{|p{6cm}|p{6cm}|}
\hline
\textbf{Tag} & \textbf{Description} \\
\hline
\texttt{<summary>} & Describes a type or member. \\
\hline
\texttt{<remarks>} & Provides additional information about a type or member. \\
\hline
\texttt{<param name="...">} & Documents a parameter, identified by the \texttt{name} attribute \\
\hline
\texttt{<typeparam name="...">} & Documents a type parameter, identified by the \texttt{name} attribute. \\
\hline
\texttt{<returns>} & Documents a return value. \\
\hline
\texttt{<value>} & Documents a property value. \\
\hline
\texttt{<exception cref="...">} & Specifies and describes an exception that may be thrown. \\
\hline
\texttt{<seealso cref="..." /> } & Specifies a link to a related type or member. \\
\hline
\texttt{<seealso href="...">} & Specifies a link to a related URL, identified by the \texttt{href} attribute. \\
\hline
\texttt{<example>} & Shows an example of how to use the type or member. \\
\hline
\end{tabular}
\caption{Top-level XML tags}
\label{table:top-level-tags}
\end{table}

The documentation is then stored inside those elements.
The only exception is the \texttt{<seealso cref="..." /> } tag, which is unpaired and thus does not have any content.
Additionally, several tags, notably \texttt{<param>}, \texttt{<typeparam>}, \texttt{<exception>}, and \texttt{<seealso>} may be present multiple times in the definition.
For instance, if a method has three parameters, there could be up to three \texttt{<param>} tags (one for each parameter).

\subsubsection*{Cref attribute}
As shown in Table~\ref{table:top-level-tags}, several tags have the \texttt{cref} attribute, which specifies that the tag references a code element, i.e., a type or a member.
For instance, if a method is somehow related to \texttt{Console.WriteLine}, we can include the following tag in its documentation: \texttt{<seealso cref="Console.WriteLine" />}.
The link to the \texttt{Console.WriteLine} should then be displayed in the resulting documentation of the given method.

However, in the XML documentation file, the attribute value is stored in a slightly different format.
The reason behind this is ambiguity, because there may be other \texttt{Console.WriteLine} method in a different namespace.
Thus, the compiler resolves the type or member and replaces it with its fully qualified name, prefixed by its kind.
In our case, the result would be 
\texttt{<seealso cref="M:System.Console.WriteLine" />} (\textit{M} denotes a method).
The whole format of the string is thoroughly described in the official documentation~\cite{csharp_xml_docs}.

\subsubsection*{Usage}

The \texttt{<summary>}, \texttt{<remarks>}, \texttt{<seealso>} and \texttt{<example>} tags can be applied to any type or member.
The other top-level tags are typically intended only for a selection of types or members, as shown in Table~\ref{table:top-level-tags-usage}.

\begin{table}[ht]
\centering
\begin{tabular}{|p{6cm}|p{6cm}|}
\hline
\textbf{Tag} & \textbf{Applicable to} \\
\hline
\texttt{<param name="...">} & methods and constructors \\
\hline
\texttt{<typeparam name="...">} & generic types and methods \\
\hline
\texttt{<returns>} & methods \\
\hline
\texttt{<value>} & properties \\
\hline
\texttt{<exception cref="...">} & methods, properties and events \\
\hline
\end{tabular}
\caption{Top-level XML tags -- usage}
\label{table:top-level-tags-usage}
\end{table}


\subsection{Inner tags}

\label{sec:inner-tags}

The documentation inside top-level tags may contain, in addition to text, other XML tags, so-called inner tags.
Typically, they affect how the text is rendered, i.e., they may specify a list of items, a paragraph, etc.
Table~\ref{table:inner-tags} shows a list of commonly recognized inner tags. 
Except for the \texttt{<paramref>}, \texttt{<see langword="...">}, and \texttt{<typeparamref>} tags, all of the other elements may contain text and other tags inside them.
Additionally, we can notice that the \texttt{<example>} tag can appear both as a top-level and an inner tag, as the official documentation includes examples in both contexts.

\begin{table}[h]
\centering
\begin{tabular}{|p{6cm}|p{6cm}|}
\hline
\textbf{Tag} & \textbf{Meaning} \\
\hline
\texttt{<c>} & inline code \\
\hline
\texttt{<code>} & block of code \\
\hline
\texttt{<example>} & example of how to use a type or member \\
\hline
\texttt{<list type="bullet">} & bullet list \\
\hline
\texttt{<list type="number">} & numbered list \\
\hline
\texttt{<list type="table">} & table \\
\hline
\texttt{<para>} & paragraph \\
\hline
\texttt{<paramref name="..."/>} & reference to a parameter \\
\hline
\texttt{<see cref="...">} & reference to a type or member \\
\hline
\texttt{<see href="...">} & reference to an URL \\
\hline
\texttt{<see langword="..."/>} & reference to a language keyword \\
\hline
\texttt{<typeparamref name="..."/>} & reference to a type parameter \\
\hline
\end{tabular}
\caption{Inner XML tags}
\label{table:inner-tags}
\end{table}

The only special tag is \texttt{<list>}, because it allows extra tags as its contents.
The \texttt{<item>} tag can be used inside any list item and specifies an item of the list.
Additionally, the \texttt{<term>} tag contains a definition of a term, while the \texttt{<description>} tag contains its explanation.
Both of these tags can be used inside the \texttt{<item>} tag.
In the case of a table-style list, \texttt{<item>} tag represents a row, while \texttt{<term>} and \texttt{<description>} tags represent individual cells.
Moreover, it is also possible to define a heading row of a table, using the \texttt{<listheader>} tag.

\subsection{Reusing the documentation}
\label{sec:reusing-docs}

There are two other commonly used tags -- \texttt{<include>} and \texttt{<inheritdoc>}, both unpaired.
The \texttt{<include>} tag allows us to import the documentation from an external XML file by specifying the file path and the path to the element to include.
When creating the XML documentation file, the compiler replaces the \texttt{<include>} tags with the actual documentation.
Thus, the \texttt{<include>} elements are not present in the resulting documentation file, meaning that we do not need to process them in any way.
It is also worth noting that this tag is unsupported in some languages, such as F\#.

The \texttt{<inheritdoc>} tag can be applied to any type and member and allows users to inherit the documentation.
When applied to a type, the documentation is inherited from the base type or an implemented interface.
The official documentation~\cite{csharp_xml_docs} does not specify what happens if, e.g., both the base type and implemented interface are documented.
When the \texttt{<inheritdoc>} is applied to a member, the documentation is taken from the base definition of the member.
This means the identical member in the base type or an implemented interface.
Again, the documentation does not specify any precedence.

The \texttt{<inheritdoc>} supports 2 optional arguments: \texttt{cref} and \texttt{path}.

\begin{itemize}
    \item The \texttt{cref} attribute explicitly specifies the type or member from which the documentation is inherited.
    This is handy, for instance, if we have two equivalent methods -- one synchronous and the other asynchronous.
    In this case, we can avoid repeating the documentation by using \texttt{<inheritdoc>} with the \texttt{cref} attribute.
    \item The \texttt{path} attribute allows us to inherit only selected XML nodes, which is configured by providing an XPath query.
    Then, only the matching nodes are inherited; in other words, we may specify to inherit only the \texttt{summary} tag, for instance.
\end{itemize}

Unlike the \texttt{<include>} element, the \texttt{<inheritdoc>} is not resolved by a compiler.
In other words, the \texttt{<inheritdoc>} tags are still present in the XML documentation file.
As a result, the documentation inheritance must be handled by the documentation generator.

\section{Further requirement analysis}
\label{sec:analysis-further-analysis}

In this section, we will analyze Requirements \ref{req:zero-conf}--\ref{req:platf-ind}, outlined in the first chapter, in more detail.

\subsection*{Zero configuration build}

As discussed earlier, Requirement~\ref{req:zero-conf} states that the generator should be easy 
to use, as the only mandatory argument should be the input.
On the other hand, the generator naturally should also offer several optional arguments, such as the output folder.
However, these options should have reasonable default values.

Next, consider a scenario in which a user generates the documentation using a custom configuration, then updates the code, and wants to regenerate the documentation.
Instead of specifying all the options again, saving the configuration in a file would be much more convenient.
This also makes it easier to share configurations with other developers.

\subsubsection*{Command line option format}

Various file formats are used for configuration.
The easiest solution would be to store the options in the same format as on the command line, 
allowing users to copy the configuration into a file. 
However, this approach brings multiple drawbacks.
First, this file format is not standardized or widely recognized, so text editors would not be capable of any text highlighting.
Another disadvantage, stemming from the lack of standardization, is that there is no easy way to recognize comments in the file.
Furthermore, we cannot use the command-line symbol for denoting comments, as it differs between various shells, which would cause inconsistency.
It is important to note that adding comments is a useful feature of the configuration file because it is often beneficial to explain the rationale behind setting a certain option to a specific value.
In conclusion, the command line option format does not seem ideal.

\subsubsection*{Selection of the configuration format}

The alternative way is to use a widely recognized configuration format, such as TOML, XML, JSON, or YAML. 
Using this approach, the disadvantages outlined above are typically resolved.
On the other hand, we lose the ability to simply copy-paste the options from the command line, although the conversion to the given format should not be complicated.

One option is to use a key-value configuration format, such as INI, as the configuration is not expected to have a hierarchical structure.
While the INI format is not fully standardized, the TOML format has a formal specification and is almost identical in structure.
However, the main downside of these formats is that they are not as widely adopted, especially compared to  XML, JSON, and YAML.
This is a disadvantage, as we should strive to use a format understood by a large share of users.

Another option is to use XML for configuration. While it is a powerful format, it often tends to be verbose, which makes it less ideal for our purposes.
Additionally, it seems to be losing popularity nowadays, in favor of JSON and YAML.
Compared to XML, JSON is more compact; however, its formal specification does not support comments, which is a considerable disadvantage.
Finally, YAML checks all boxes: it is widely used, supports comments, and has an even more compact syntax than JSON, which makes it an ideal choice. 
Based on the insights above, we can introduce two sub-requirements of Requirement~\ref{req:zero-conf}:

\setcounter{subrequirementcounter}{1}
\begin{subrequirement}
    Provide reasonable default values for command line arguments.
    \label{subreq:config-default-values}
\end{subrequirement}

\begin{subrequirement}
    Support configuration using a YAML file.
    \label{subreq:config-yaml}
\end{subrequirement}

\subsection*{Custom templates}

Next, the generator should be designed to be extensible, as described in Requirement~\ref{req:templates}.
The documentation pages will naturally be generated from templates, written in an unspecified templating language, which get populated with data while the documentation is generated.

First, if users wanted to define a custom UI using the same templating language and data, providing the equivalent templates should suffice.
In other words, if the generator had two templates representing the \textit{type} and \textit{namespace} pages, supplying a custom version of these two should be enough.

Furthermore, users should be able to write their own templates in a templating language of their choice,
using the provided data representing the types and members.
In addition to templates themselves, the users should also provide a code that generates them.
In practice, this should be done by implementing a corresponding interface.
This allows us to define the following two sub-requirements:

\setcounter{subrequirementcounter}{2}
\setcounter{subrequirement}{0}

\begin{subrequirement}
    The generator should allow users to define templates written in the same templating language as the default UI.
    \label{subreq:custom-razor-templates}
\end{subrequirement}

\begin{subrequirement}
    The generator should allow users to define templates written in a templating language of their choice, accompanied by the code that generates them.
    \label{subreq:custom-template-lang}
\end{subrequirement}

\subsection*{Custom static pages}

Requirement~\ref{req:static-pages} mentions support for user-specified static pages.
As discussed before, the goal is not to create a full-fledged SSG; instead, a convention-based approach with no configuration is preferred.
A simple yet effective approach would be to give the user an option to include a folder containing static pages.
The generator should then recursively copy the files from the folder into the output directory, thus including the pages in the documentation.
Also, note that the relative paths between files stay the same because the directory structure is preserved.
As a result, the links between files can stay intact, which is a huge advantage of this approach.

Regarding pages, we must consider several formats that users may want to use.
The natural option is to use HTML, as the resulting page will be in HTML format.
Moreover, we also want to support Markdown, since it is extremely popular these days and easy to write.
In addition to pages, the folder may contain other non-page files, such as CSS, JavaScript, or images, so we need to handle those as well.
As a result, we can further clarify Requirement~\ref{req:static-pages}:

\setcounter{subrequirementcounter}{3}
\setcounter{subrequirement}{0}

\begin{subrequirement}
    Option to select a folder containing static files to be included in the documentation. 
    \label{subreq:static-pages-folder}
\end{subrequirement}

\begin{subrequirement}
    Support static pages in both HTML and Markdown format.
    \label{subreq:static-pages-format}
\end{subrequirement}

\subsection*{Documentation versioning}
\label{sec:doc-versions}

Requirement~\ref{req:versioning} focuses on documentation versioning.
The generator should support an option (both on the command line and in the configuration file) for creating a specific version of the documentation, e.g., \textit{v1.2}. 
The resulting documentation should then be stored not in the output folder, but in its subfolder identified by the version number (\textit{v1.2} in our case).
This way, the output folder may contain multiple versions of the documentation.

Additionally, the default UI should allow users to switch between different versions.
To achieve this, the UI should include a dropdown showing the available versions.
Whenever a new version of the documentation is generated, all the older versions should be updated to include the most recent version in the dropdown.
Thus, we can define the following two sub-requirements:

\setcounter{subrequirementcounter}{4}
\setcounter{subrequirement}{0}

\begin{subrequirement}
    Option to create a specific version of the documentation.
    \label{subreq:doc-version-option}
\end{subrequirement}

\begin{subrequirement}
    Provide a dropdown menu in the UI allowing users to select the documentation version.
    \label{req:doc-version-dropdown}
\end{subrequirement}

We have skipped Requirements~\ref{req:lang-ind}, \ref{req:modern-ui}, and~\ref{req:platf-ind}, as they remain unchanged.
Furthermore, since we have decided to extract the context data from an assembly, Requirement~\ref{req:lang-ind} is automatically satisfied, as discussed earlier.

First and foremost, we would like to have an index page of the API showing all namespaces contained in an assembly.
Additionally, under each namespace, there should be a list of types declared inside it.
Thus, our eighth requirement is:

\begin{requirement}
    Index page of the API.
    \label{req:index-page}
\end{requirement}

\setcounter{subrequirementcounter}{8}
\setcounter{subrequirement}{0}

\begin{subrequirement}
    Show a list of namespaces.
\end{subrequirement}

\begin{subrequirement}
    Show a list of types declared in each namespace.
\end{subrequirement}

Next, there should be a page for each namespace, displaying all the contained types.
For each type, there should be a link to its definition and its documentation, which leads us to the following requirement:

\begin{requirement}
    Separate page for each namespace.
    \label{req:namespace-page}
\end{requirement}

\setcounter{subrequirementcounter}{9}
\setcounter{subrequirement}{0}

\begin{subrequirement}
    Show a list of types declared in the namespace.
\end{subrequirement}

Finally, there should be a separate page for each type displaying its signature in C\# format and documentation.
The documentation should be divided into sections, corresponding to top-level XML tags.
In addition to that, there should be a section displaying the attributes applied to a type.
So, the documentation may contain those sections (each section should be displayed only if the corresponding tag is present):

\begin{itemize}
    \item \textit{Summary} (corresponding to the \texttt{<summary>} tag)
    \item \textit{Remarks} (corresponding to the \texttt{<remarks>} tag)
    \item \textit{Example} (corresponding to the \texttt{<example>} tag)
    \item \textit{Type parameters} (corresponding to the \texttt{<typeparam>} tags)
    \item \textit{See also} (corresponding to the \texttt{<seealso>} tags)
    \item \textit{Attributes} (displaying the attributes)
\end{itemize}

Then, we have two options: show the list of members on the type page, as \textit{DocFX} and \textit{Doxygen} do, or have a separate page for each member, similar to the official .NET documentation and \textit{SHFB}.
Since we aim to generate reference documentation for third-party libraries, which are usually not as extensively documented as the .NET API, 
having a separate page per member would likely be unnecessarily complex.
Thus, the list of declared members should be displayed below the type definition. The members should be grouped into categories based on their kind (field, property, method, etc.), similar to \textit{SHFB}.
Each member should again display the signature and the documentation, corresponding to the XML tags, along with the section displaying attributes.
So, potentially, the member documentation can contain the following sections:

\begin{itemize}
    \item \textit{Summary} (corresponding to the \texttt{<summary>} tag)
    \item \textit{Remarks} (corresponding to the \texttt{<remarks>} tag)
    \item \textit{Example} (corresponding to the \texttt{<example>} tag)
    \item \textit{See also} (corresponding to the \texttt{<seealso>} tags)
    \item \textit{Type parameters} (corresponding to the \texttt{<typeparam>} tags)
    \item \textit{Returns} (corresponding to the \texttt{<returns>} tag)
    \item \textit{Param} (corresponding to the \texttt{<param>} tag)
    \item \textit{Value} (corresponding to the \texttt{<value>} tag)
    \item \textit{Attributes} (displaying the attributes)
\end{itemize}

This gives us another requirement:

\begin{requirement}
    Separate page for each type.
    \label{req:type-page}
\end{requirement}

\setcounter{subrequirementcounter}{10}
\setcounter{subrequirement}{0}

\begin{subrequirement}
    Show type signature in C\# format.
\end{subrequirement}

\begin{subrequirement}
    Show type documentation, divided into sections corresponding to XML tags.
\end{subrequirement}

\begin{subrequirement}
    Show signatures of all members contained in the type.
\end{subrequirement}

\begin{subrequirement}
    Show documentation of all members, divided into sections corresponding to XML tags.
\end{subrequirement}

Next, there should be a menu at the top of each page, which should include links to the API index page and all pages stored in the user-specified folder with static files.
On top of that, each subfolder of the static files folder should be represented by a dropdown menu, displaying the pages stored directly within the subfolder.
Static pages located three or more levels deep will not be included in the menu.
In conclusion, we can formulate the requirement as follows:

\begin{requirement}
    Display the top menu on each page.
    \label{req:top-menu}
\end{requirement}

Moreover, the top menu should include a search bar, allowing users to search for types and members.
If a user tries to search for something, he/she will be redirected to the search page showing a list of results.

\begin{requirement}
    Search functionality.
    \label{req:search}
\end{requirement}

\setcounter{subrequirementcounter}{12}
\setcounter{subrequirement}{0}

\begin{subrequirement}

\end{subrequirement}

\begin{subrequirement}
    Show a list of results at the \textit{search} page.
\end{subrequirement}

Thus, our next requirement is:

\begin{requirement}
    Correctly interpret the inner XML tags.
    \label{req:inner-xml-tags}

\begin{requirement}
    Resolve \texttt{<inheritdoc>} tags.
    \label{req:inheritdoc}
\end{requirement}

All of the generators also have support for cross-references.
This means that member, parameter, and return types contain a link to their definition, if possible.
The same applies to the types and members referenced in documentation comments using \texttt{<see>} or \texttt{<seealso>} tags with the \texttt{cref} attribute.
Support for the types declared in the same project is mandatory, and optionally, we can also add links to standard library types.
This gives us another requirement:

\begin{requirement}
    Support for cross-references.
    \label{req:cross-ref}
\end{requirement}

Additionally, we should consider that some users prefer a light theme, while others may favor a dark one.
In the official .NET documentation, users can switch between themes using a dropdown, as shown in Figure~\ref{fig:official-themes} (A).
The Figures~\ref{fig:official-light} and~\ref{fig:official-dark} display the same page in both light and dark themes.

Among the generators, the support for a dark theme varies.
\textit{Doxygen} has a built-in dark mode that can be toggled using a button; however, this functionality must be explicitly enabled by setting a corresponding option.
The default UI of \textit{DocFX} does not support dark mode; however, \textit{DocFX} offers a variety of templates, such as the \textit{modern} template, which supports both light and dark modes. 
Again, it is possible to switch between themes using a button.
Moreover, multiple \textit{DocFX} templates are exclusively dark-themed.
Finally, \textit{SHFB} has neither built-in support for dark mode in the default UI nor a dark-themed template.
In conclusion, our generator should support both light and dark themes, with an option to easily switch between them, which is our next requirement:

\begin{requirement}
    Support both light and dark themes.
    \label{req:dark-theme}
\end{requirement}

Next, although reference documentation is primarily viewed on laptops and desktops, there are cases where users may browse it on tablets or mobile phones. 
This means the UI should be reasonably responsive to accommodate this usage. 
The default UIs of all generators are responsive as well, which leads us to the following requirement:

\begin{requirement}
    Responsive UI.
    \label{req:responsive}
\end{requirement}

Another thing to consider is that the official .NET documentation, as well as the other generators, support displaying the reference documentation in various other .NET languages, such as F\# and VB.NET.
As a result, the displayed type and member signatures may change based on the selected language, while the language itself can typically be selected using a dropdown.
We do not aim to include support for languages other than C\# in the default UI, as previously explained in Requirement~\ref{req:lang-ind}; however, the default UI should be designed with extensibility in mind so that support for additional languages can be added in the future without major restructuring.
Moreover, the same applies to the generator itself.
Thus, the next requirement can be stated as follows:

\begin{requirement}
    The generator and its default UI must be designed to allow future support for additional programming languages.
    \label{req:ui-multiple-langs}
\end{requirement}

It is also worth noting that the official .NET documentation can be browsed in various spoken languages, besides English.
While localization may be helpful in official documentation, particularly for beginner developers who are less fluent in English, it is generally unnecessary for reference documentation of software libraries.
This is because most developers are expected to understand English, especially as the API of the library is typically not localized either.
Furthermore, seeing technical terms in a local language might be confusing for many developers, as English is the primary language of computer science.
Therefore, we do not plan to support localization, similarly to \textit{DocFX}, \textit{Doxygen}, and \textit{SHFB}.

\section*{Other requirements}
In previous sections, we thoroughly described Requirements \ref{req:zero-conf}--\ref{req:platf-ind} introduced in the first chapter. 
Next, we stated multiple other requirements based on the analysis of existing documentation generators and the official .NET documentation.
In this section, we will present the remaining requirements, based on various use cases.

The first important observation is that the program to be documented may consist of multiple projects, contained in a solution. 
In this case, users typically want to include these projects in the documentation.
However, not all projects in the solution need to be included; for instance, users often prefer to exclude the ones containing tests. 
Thus, there should be a way to exclude selected projects from the resulting documentation.
Considering these points, we can introduce the following two requirements:

\begin{requirement}
    Option for selecting a solution as the input.
    \label{req:solution-as-input}
\end{requirement}

\begin{requirement}
    Option to exclude selected projects from the documentation.
    \label{req:exclude-assemblies}
\end{requirement}

Additionally, the project itself may contain certain types we would like to exclude from the documentation.
For instance, consider an app that includes \textit{Razor} templates, which get compiled into .NET classes.
As a result, they would normally appear in the documentation, which is usually undesirable.

One option would be to use an extra XML tag (for instance \texttt{<ignore>}), allowing the developers to mark types that should be excluded from the documentation. 
However, this approach brings a significant disadvantage, as it creates a coupling between the program and the generator.
In other words, the program developers must be aware of the documentation generator.

An alternative solution is to support an option that allows users to exclude types based on their namespaces, as in most cases, these types are contained within the same namespace.
This approach eliminates the dependency between the code and the generator.
Thus, we can formulate the subsequent requirement:

\begin{requirement}
    Option to exclude types in selected namespaces.
    \label{req:exclude-namespaces}
\end{requirement}

As discussed in Section~\ref{section:context}, reference documentation is primarily intended for developers using a library or maintainers of the library.
In the first case, only the public API is relevant, so public members alone are enough, while in the second case, it often makes sense to include non-public members as well.
This gives us another requirement:

\begin{requirement}
    Option for selecting types and members based on their accessibility level.
    \label{req:exclude-accessibility}
\end{requirement}

It is also worth noting that users may want to exclude inherited members from the documentation, based on different use cases.
For instance, it may be preferred to exclude inherited members to focus solely on the specific API exposed by the types. 
As a result, we can formulate the following requirement:

\begin{requirement}
    Option for including/excluding the inherited members.
    \label{req:exclude-inherited}
\end{requirement}

Last but not least, we should consider the program installation.
Ideally, the installation method should be cross-platform and allow for easy updates.
The first option is to install the generator as a standard executable app. 
However, this approach has multiple disadvantages; for instance, the installation typically needs to be done manually.
In addition to that, the same applies to updates.

Fortunately, there is an alternative option: install the generator as a .NET tool.
As described in the documentation~\cite{dotnet_tools}, a .NET tool is a special type of a NuGet package, containing a console application.
.NET tools can be installed from the command line by running \texttt{dotnet tool install} and then invoked from the command line as well.
Updates are also easy, as the tool can be updated simply by running the \texttt{dotnet tool update} command.

In conclusion, installation as a .NET tool meets all criteria, and thus seems like a reasonable choice, leading us to the last requirement:

\begin{requirement}
    The generator should be distributed as a .NET tool.
    \label{req:dotnet-tool-dist}
\end{requirement}
