\chapter{Technical Analysis}

In the previous chapter, we formulated several requirements that the documentation generator should adhere to.
This chapter presents a thorough analysis of the solution, examining its structure and addressing numerous challenges to ensure these requirements are met.

\section{Member representation}
\label{sec:member-repr}

First, we can notice that we must somehow represent type members in our codebase.
That is because we need to know their names and various data concerning them. 
For instance, it is mandatory to know whether a member is static, public, etc., as this information needs to be included in the reference documentation.
Additionally, we need to display the corresponding documentation comments.

\subsection*{Using the types provided by reflection}
The first idea is to use the objects provided by reflection, such as \texttt{FieldInfo} and \texttt{MethodInfo}, which provide the data we need to display.
For instance, it is possible to obtain the name of a member, in addition to that 
these types contain properties such as \texttt{IsStatic}, \texttt{IsPublic}, etc.

However, as explained earlier, the documentation comments are not part of the assembly. 
Therefore, these types do not contain any data regarding the documentation comments.
Since we need to somehow extract the comments, we can conclude that using the types provided by reflection alone is not sufficient.

The first option is to simply pass the XML documentation file along with the members.
When obtaining the documentation comment, we would call e.g. \texttt{xmlDocFile.GetDocComment(memberName)}.
However, there are multiple issues with this approach.

As described in the Requirement~\ref{req:templates}, the generator should be designed in an extensible way.
Thus, in the future, this API may be used by other developers, and therefore it should be as intuitive as possible.
Unfortunately, the approach above does not create a particularly intuitive interface. 
The main problem is that the concerns are mixed, as the data regarding the member is stored within the type, while the documentation needs to be extracted separately.

\subsection*{Using a tuple}

This leads us to an alternative approach: representing members as a tuple containing the reflection object and the corresponding documentation comment.
By doing so, we address some of the issues outlined above; specifically, we achieve better cohesion by storing the documentation alongside the reflection object itself.

However, several problems persist.
The user still needs to parse the documentation in order to obtain the individual top-level tags, because those typically should be displayed in a different way.
Furthermore, that API is still quite messy, since it contains, e.g., a method setting a field's value, and additional methods irrelevant to documentation generation.

In addition to that, handling different kinds of members (e.g., properties and methods) in the program in a common way can be complicated.
That is caused by the design of the .NET Reflection API, as e.g., there is no common superclass or interface for properties and methods, other than \texttt{MemberInfo}.
However, this class provides only a handful of information about a member, specifically, it is not possible to determine whether the member is static or its accessibility level.

\subsection*{Using custom types}

Instead of the reflection types, we can use custom types for the member representation.
Ideally, those types could be simply wrappers around the built-in reflection types, providing extra information, such as the documentation comments.
Moreover, the fields and methods not relevant to documentation generation do not need to be included in the API, as we want to keep the interface as clean as possible.
This way, we can achieve a user-friendly object model, where all member types can have the following structure:

\begin{itemize}
    \item name
    \item whether it is static
    \item accessibility (private, public, etc.)
    \item + other member-related information
    \item summary documentation
    \item remarks documentation
    \item + other documentation-related information
\end{itemize}

Furthermore, we can create custom interfaces or supertypes for a certain set of members that share common functionality. As an example, there could be a common interface for properties and methods, which allows us
to process those in a common way in other parts of our code base.

Based on these insights, we will prefer this approach.

\section{Type representation}
\label{sec:type-repr}

We have already decided how to represent type members, yet a similar question is relevant for types as well, as the types will also be included in the documentation.
One option is to use the built-in \texttt{System.Type} class, however, since we have already decided to use custom member classes, it would bring multiple drawbacks.

Notably, there is no way to store the members of custom types inside an existing class.
Next, the API of \texttt{System.Type} is not particularly clean for our purpose, for the same reasons as mentioned in the previous section.

Thus, it would be preferred to create custom types representing the types, with the following structure:

\begin{itemize}
    \item name
    \item + other type-related information
    \item fields
    \item properties
    \item methods
    \item + other member-related information
    \item summary documentation
    \item remarks documentation
    \item + other documentation-related information
\end{itemize}

\section{Assignment of the documentation comments}

We have already described how to represent types and members in our codebase.
However, we have not yet explained how to assign the documentation to the corresponding types or members.
As explained in Section~\ref{section:xml-doc}, the documentation comments are stored inside the XML documentation file, whose format was already presented in Program~\ref{lst:ex-xml-output}.
We have also noted that the \texttt{name} attribute uniquely identifies the type or member to which the documentation belongs.
An example of the ID string is shown in Program~\ref{lst:ex-xml-string}.

The format of the string is thoroughly described in the documentation~\cite{csharp_xml_docs}.
Generally, it consists of two parts, separated by a colon. 
The first part identifies the kind of the type or member, for example, \textit{T} is used for types, \textit{M} for methods, \textit{F} for fields, etc.
Additionally, the second part represents a fully qualified name of the type or member.
In the case of a member, the name consists of the containing type name followed by the member name.
If there are any parameters, they are enclosed in parentheses and identified by their type names.
Thus, the string shown in Program~\ref{lst:ex-xml-string} identifies a method \texttt{CalculateRectangleArea}, 
which is contained within the type \texttt{MyApp.MyClass} and takes two parameters of type \texttt{System.Double}.
This way, we can find the corresponding type or member for the comment.

Thus, the generator can process the XML file, find all documentation comments, and assign them to the corresponding types or members, one by one.

\begin{listing}[H]
\begin{lstlisting}[language=XML]
<member name="M:MyApp.MyClass.CalculateRectangleArea
                            (System.Double,System.Double)">
\end{lstlisting}

\label{lst:ex-xml-string}
\end{listing}

\section{Resolving \texttt{inheritdoc} tags}

As mentioned in Requirement~\ref{req:inheritdoc}, our generator must be capable of resolving \texttt{<inheritdoc/>} tags.
The key observation is that they may be used recursively, i.e., the resolved documentation may again contain \texttt{<inheritdoc/>} tags.
Program~\ref{lst:ex-doc-classes} shows an example class hierarchy with inherited documentation comments.
As we can see, \texttt{ChildChild} class inherits its documentation from \texttt{Child} class, 
which inherits it from \texttt{Parent} class.
Thus, after resolution, all three classes should have the same documentation comment -- \textit{"Parent class."}.
Hence, the resolution may be done using depth-first search.
Moreover, Program~\ref{lst:ex-doc-classes} shows that \texttt{ChildChild.Handle} method inherits the documentation from \texttt{Child.Handle} method, 
while \texttt{Child.Handle} uses the documentation provided to \texttt{Console.WriteLine} method.

\begin{listing}[H]
\begin{lstlisting}
/// <summary>
/// Parent class.
/// </summary>
public class Parent
{
    /// <summary>
    /// Handle method.
    /// </summary>
    public virtual void Handle()
    {
    }
}

/// <inheritdoc/>
public class Child : Parent
{
    /// <inheritdoc cref="Console.WriteLine()" />   
    public override void Handle()
    {
    }
}

/// <inheritdoc/>
public class ChildChild : Child
{
    /// <inheritdoc/>
    public override void Handle()
    {
    }
}
\end{lstlisting}
\caption{Example class hierarchy with inheritdoc tags}
\label{lst:ex-doc-classes}
\end{listing}

As mentioned before, the \texttt{<inheritdoc/>} tag may be applied to both types and members, and may contain \texttt{cref} attribute.
Therefore, we can identify the following three cases, whose resolution fundamentally differs:

\begin{itemize}
    \item \texttt{<inheritdoc/>} applied to a type (without \texttt{cref} attribute)
    \item \texttt{<inheritdoc/>} applied to a member (without \texttt{cref} attribute)
    \item \texttt{<inheritdoc/>} with \texttt{cref} attribute
\end{itemize}

The resolution rules were already described in section~\ref{sec:reusing-docs}, however, we briefly recapitulate them here for convenience.
In the first case, we must locate the base type and all implemented interfaces,
while the second case requires identifying all equivalent definitions of the member in those types.
Finally, in the last case, we need to find the corresponding type or member by its ID string contained in the \texttt{cref} attribute.

Next, consider a method inheriting documentation from its base definition, where that base definition itself inherits the documentation using \texttt{cref} attribute. 
This is exactly the case of \texttt{ChildChild.Handle} and \texttt{Child.Handle} methods shown in Program~\ref{lst:ex-doc-classes}.
This situation complicates the resolution process, as we first need to identify the correct case out of the three before proceeding.

A simple observation is that we can first resolve the tags without the \texttt{cref} attribute. 
During this process, we can possibly copy some of the \texttt{<inheritdoc/>} tags with \texttt{cref}, however, this is not a problem, as these point to a fixed target.
Then, in the second phase, we can resolve all tags with the \texttt{cref} attribute.
This simplifies the process a little bit, as at one time we need to handle only one kind of \texttt{<inheritdoc/>} tags.

\section{Templating language choice}

In the previous chapters, we described how to represent types and members, as well as how the documentation is assigned to them.
Yet, we still have not discussed the generation of the documentation pages.
Technically, it is possible to use no templating language at all, in other words, to
generate the HTML manually by building the DOM tree. However, this approach
quickly becomes cumbersome and hard to maintain, as the templates grow bigger.
Thus, we need to select a proper templating language, as outlined in Requirement~\ref{req:templates}.

\subsection*{Context}

Before we proceed with the comparison of various templating languages, we should introduce a bit of context to aid understanding.
First, a templating language is used for writing templates, which are essentially files with static content and placeholders intended to be replaced with variable data. 
In order to generate the resulting file, the variables must be provided, along with the template itself.
This process is accomplished using a template processor, which takes both the template and variables as its input and creates the resulting file.
Template processors are often distributed as software libraries, so processing a template can typically be achieved simply by calling a method.

It is also important to note that variables in templating languages can have different types.
While the set of supported types varies depending on the language, most templating languages support at least strings, booleans, and lists.
Furthermore, structured objects are typically supported as well.

Arguably, the main advantage of using such a templating language is that users can easily generate files with the same structure but different content.
For instance, we can create a template representing a type page, as requested in Requirement~\ref{req:type-page}.
Then, we can create many such pages simply by providing the corresponding variables, such as the type name, its members, etc.

\subsection*{Key templating language features}

Next, before we move on to the individual templating languages, it is necessary to establish several essential features that a language must provide in order to be considered suitable.
First, we require conditional rendering because some text should be rendered only if a certain condition is met.
As an example, consider a \textit{Remarks} section, which should be displayed only if a \texttt{<remarks>} tag is present.
Therefore, the templating language must support conditions.
In addition, support for iteration is also mandatory, as we will need to list all fields, methods, etc., contained in a type.
Thus, the language should provide loops as well.

\label{sec:templating-language-importing}
Another key observation is that certain parts of the UI might be reused in multiple places.
Consider, e.g., the \textit{Type parameters} section, displaying type parameters and their documentation, which can be present at both method and type definition.
The same idea can be applied in many other places, for instance, each member and type can possibly contain the \textit{Remarks} and \textit{See also} sections.
Furthermore, the same goes for the top menu, mentioned in Requirement~\ref{req:top-menu}, as it should be displayed on each page.
The natural solution is to extract the common code (e.g., the \textit{Type parameters} section) into a separate template and then import it.
On top of that, certain data usually needs to be passed into the imported templates. 
For example, the \textit{Type parameters} template would require the type parameters data.
Hence, the templating language must support importing other templates, which is, fortunately, quite a common feature.

\subsection{Mustache}

Mustache~\cite{mustache} is a simple templating language that allows users to replace certain parts of the file with variable contents, enclosed in double curly braces.
For instance, the \texttt{\{\{name\}\}} placeholder is, during template processing, replaced by the value of the \texttt{name} variable.

The fundamental idea behind Mustache is that the templates should contain as little logic as possible.
Instead, the logic should be done in the code, and the templates should be used purely for rendering.
That is why it does not support, for instance, comparing a value to a constant. 
For instance, we cannot check if a person is an adult by comparing his/her age to 18, as this is not allowed in mustache templates.
Instead, we should declare a variable named, e.g., \texttt{isAdult} in the code and pass it into the template.

While \textit{mustache} directly does not support conditions or loops, it is possible to achieve similar behaviour using a special language construct -- sections.
A section requires a variable and is rendered zero or more times, depending on the variable value, as stated in the documentation~\cite{mustache}. 
If the variable is \texttt{false} or an empty list, the section is not rendered at all.
On the other hand, if the variable is a non-empty list, the section contents will be displayed once for each item.
This way, we can simulate conditions and loops, respectively.
Additionally, if neither of those cases applies, the section is rendered exactly once.
Syntactically, a section begins with a hash sign and ends with a slash. 
For example, \texttt{\{\{\#person\}\}} begins a \textit{person} section while \texttt{\{\{/person\}\}} ends it.
There can be arbitrary content inside the section.
Additionally, inside the section, the current item can be referenced by using \texttt{\{\{.\}\}} tag.

Program~\ref{lst:mustache} shows an example of a mustache template, which displays the provided name and age.
Then, if the \texttt{isAdult} property is not false, the template should also include the information that the person is an adult.
Finally, all owned items (i.e., all items contained in \texttt{itemsOwned} list) are shown as an unordered list.

\begin{listing}[H]
\begin{lstlisting}[language=HTML]
<p>
    <div>
        Name: {{name}}
    </div>
    <div>
        Age: {{age}}
    </div>
    
    {{#isAdult}}
    <div>
        This person is an adult.
    </div>
    {{/isAdult}}
    
    <div>
        Items Owned:
        
        <ul>
        {{#itemsOwned}}
            <li>
                {{.}}
            </li>
        {{/itemsOwned}}
        </ul>
    </div>
</p>
\end{lstlisting}
\caption{Example mustache template}
\label{lst:mustache}
\end{listing}

  \item \texttt{age: 15}

\subsection{Handlebars}

Handlebars~\cite{handlebars} is another widely used templating language.
Its syntax is very similar to Mustache and covers almost all of its functionality.
However, it introduces slightly different syntax for conditions and loops, using the \textit{if} and \textit{each} keywords.
Moreover, the conditions can be evaluated only against true/false, so it is not possible to check, e.g., whether a number is greater than a given value.
On the other hand, unlike mustache, it is possible to add extra functionality through the use of custom helpers.
A helper is simply a function written by a user in a given programming language that is registered and then evaluated during template processing.
For instance, we can write a custom helper that compares two numbers or converts a string to uppercase.

An example of a Handlebars template is displayed in Program~\ref{lst:handlebars}.
We can also notice that a custom helper -- \texttt{geq} is used to check whether a person is an adult.
Additionally, before the template is processed, we need to register the helper by providing its code.
As a result, unlike mustache, declaring the \texttt{isAdult} variable is unnecessary.
Though Handlebars templates are primarily intended for JavaScript, .NET is also supported using the Handlebars.NET library~\cite{handlebars_net}.

\begin{listing}[H]
\begin{lstlisting}[language=HTML]
<p>
    <div>
        Name: {{name}}
    </div>
    <div>
        Age: {{age}}
    </div>
    
    {{#if (geq age 18)}}
    <div>
        This person is an adult.
    </div>
    {{/if}}
    
    <div>
        Items Owned:

        <ul>
        {{#each itemsOwned}}
            <li>
                {{this}}
            </li>
        {{/each}}
        </ul>
    </div>
</p>
\end{lstlisting}

\label{lst:handlebars}
\end{listing}

\subsection{Liquid}

Another, more complex templating language is Liquid~\cite{liquid}.
Again, its syntax and functionality are quite similar to Mustache and Handlebars.
However, unlike them, it supports a wide range of filters that can be used for output customization.
Filters are functions used to change the output of a variable; for instance, the \texttt{upcase} filter converts the input string into uppercase. 
Syntactically, filters are separated by a pipe character.
Thus, we can, e.g., print the name of a person in uppercase by the following code: \texttt{\{\{ name | upcase \}\}}.
Furthermore, Liquid supports all commonly used comparison operators as well as the \textit{and} and \textit{or} boolean operators, and using custom variables.
An example of a Liquid template is shown in Program~\ref{lst:liquid}.

Although the Liquid language itself does not specify support for custom filters, this functionality is typically provided by the libraries processing Liquid templates.
In .NET, Liquid templates can be processed using the DotLiquid~\cite{dotliquid} library, however, this library directly states that it is looking for maintainers, therefore, its future is unclear.
Additionally, there are two other popular .NET libraries: Scriban~\cite{scriban} and Fluid~\cite{fluid}, which use a custom language that is almost identical to Liquid, with a range of extra filters added.

\begin{listing}
\begin{lstlisting}[language=HTML]
<p>
    <div>
        Name: {{ name }}
    </div>
    <div>
        Age: {{ age }}
    </div>
    {% if age >= 18 %}
    <div>
        This person is an adult.
    </div>
    {% endif %}
    <div>
        Items Owned:
        {% for item in itemsOwned %}
            <div>{{ item }}</div>
        {% endfor %}
    </div>
</p>
\end{lstlisting}

\subsection{Razor}

Finally, it is also possible to use Razor markup language~\cite{razor}.
The major difference between Razor and other previously mentioned templating languages is that Razor allows embedding fragments of C\# code.
As a consequence, it naturally supports C\# language constructs, such as conditions, loops, functions, etc.
The transition to C\# is done using the at sign; thus, the expression \texttt{@name} renders the value of the variable \texttt{name}.
Furthermore, it is also possible to include whole blocks of C\# code, enclosed in \texttt{@\{} and \texttt{\}}.
As mentioned before, there could be arbitrary C\# code inside the code block.

An example of a Razor file is shown in Program~\ref{lst:razor}.
As we can see, the object of type \texttt{Person} is passed to the template.
The processing of Razor files can be done using the RazorLight library~\cite{razor_console}, however, certain constructs, such as methods, are not supported.
Additionally, even though Razor was originally intended for use in web applications, it is also possible
to use Razor components and render them in console applications, as mentioned in the official documentation~\cite{razor_console}.

\begin{listing}[H]
\begin{lstlisting}[language=HTML]
<p>

    <div>

        </div>
    }

        Items Owned:

        <ul>
        @foreach (var item in Person.ItemsOwned)

\subsection*{Evaluation of templating languages}

We have presented several templating languages, starting from the simplest to the most powerful.
As previously discussed, all of them support using conditions and loops; however, in Mustache, the support for conditions is very basic.
Thus, if we decided to use Mustache, adding several conditional boolean fields to the data would likely be inevitable.

Consequently, it is important to note that all of the languages mentioned support importing templates. 
On top of that, most languages also support passing parameters to them.
The only exception is Mustache, where the imported template inherits the variables of the calling one.
Although this is sufficient in many cases, it may become a limiting factor.

For instance, consider the cross-reference links mentioned in Requirement~\ref{req:cross-ref}.
These links should have the same style and functionality, so it is a good idea to extract the code into a separate template to avoid duplication. 
The template can then be used for displaying the type of a field, the return type of a method, the parent type of a type, and so on.
Next, assume that inside the template, we refer to the variable denoting type as \texttt{type}.
This means that in the context of a field object, its type must be stored in a \texttt{type} variable.
However, the same goes for a method and its return type, as it also needs to be stored in a \texttt{type} variable in the context of a method object.
More specifically, the natural name \texttt{returnType} for denoting the return type of a method cannot be used, as in the cross-reference link template, the variable is called \texttt{type}.
This is a considerable disadvantage, as the variables passed to the template need to have a certain structure because of Mustache.
On the other hand, in the remaining languages, which allow us to pass parameters, we could still refer to the return type of a method as \texttt{returnType}.
Then, when importing the cross-reference link template, we would just pass this value to the \texttt{type} parameter.
Consequently, these drawbacks suggest that Mustache is not an ideal choice.

Next, even though both Handlebars and Liquid are suitable options, Razor has a big advantage by using static typing.
This stems from the fact that when using Razor, we need to specify the types of the variables passed to the template.
As a result, many errors, such as a mistyped variable name or type, can be detected at compile time, which greatly simplifies the development process, especially as the templates are expected to be non-trivial.
Without static typing, we would need to include a variety of tests covering all conditions in the template to ensure that the output is as expected.
This leads us to the conclusion that Razor is the most suitable choice.
Additionally, we will prefer using Razor components over the RazorLight library due to the limitations discussed in the previous section.

It is crucial to mention that the selection of Razor applies only to the default UI, as the generator should be completely independent of the templating language.
This means that it should be easily possible to add support for other templating languages by adding a set of templates and the code that calls the template processor, as requested by Requirement~\ref{subreq:custom-template-lang}.
Hence, if a user decides to write templates in, e.g., Liquid language, he/she must provide the code calling the Liquid template processor in addition to the templates.
Once the support for Liquid is added, other users can reuse this code and possibly include custom Liquid templates.

\section{Template models}

Next, we must consider what objects should be passed into the templates.
A straightforward option is to use the custom objects representing the types and members, introduced in sections~\ref{sec:member-repr} and~\ref{sec:type-repr}.
We should remember that the documentation should display, e.g., if a method is static, virtual, abstract, etc.
While the method object contains this information, it will be stored in fields \textit{IsStatic}, etc.

Thus, the templates must include logic checking whether a member is static to determine whether the \textit{static} keyword should be included in its definition.
The same applies to other keywords, such as \textit{abstract}, \textit{virtual}, etc.
Moreover, if a user creates a custom template, as described in the requirement~\ref{req:templates}, the logic must be duplicated there.

The alternative option is to use special objects intended only for use in templates, called template models.

\section{UI framework}

There are many ways to achieve a modern, visually appealing UI, as requested by Requirement~\ref{req:modern-ui}.
It is also crucial to mention that this applies only to the default UI, since user-created templates may use totally different framework.
More specifically, the default UI is expected to include the top menu, search bar, dropdowns, links, etc., as mentioned in Requirements~\ref{req:top-menu}, \ref{req:search-bar}, \ref{req:doc-version-dropdown}, and~\ref{req:cross-ref}.
Furthermore, the dark theme should be supported, as stated in Requirement~\ref{req:dark-theme}.
Additionally, according to Requirement~\ref{req:responsive}, the UI should be responsive.

The first option is to write custom CSS and possibly JavaScript. 
However, creating modern-looking responsive UI components is by no means a trivial task, so as a consequence, there are many CSS libraries available.
The most popular ones as of today are \texttt{Bootstrap}~\cite{boostrap}, and
\texttt{Tailwind CSS}~\cite{tailwind}. 
There is a fundamental difference in philosophy between those libraries, as \texttt{Bootstrap} is primarily a component library, providing pre-styled components.
For instance, there is a CSS class for a navigation bar, dropdown, button, etc.
In contrast, \texttt{Tailwind CSS} offers a large set of CSS utility classes that can be used to build custom components.
For example, Tailwind offers CSS classes for setting width, margin, background color, font, etc.
By combining those classes, we may create, e.g., a styled dropdown.
Thus, creating UIs with Tailwind is more complex; on the other hand, it offers great flexibility, because we can combine the utility classes as we want.
While Tailwind also offers pre-styled components, such as dropdowns and navigation bars under Tailwind Plus, a major disadvantage is that only a handful of them are available in the free tier.

Additionally, Bootstrap has good support for dark theme, which can be achieved just by adding the \texttt{data-bs-theme="dark"} attribute to the HTML body, as described in the official documentation.
In Tailwind, it is slightly more verbose, as we need to define a set of utility classes for the dark style of each component.
Finally, responsivity is well-supported in both frameworks.
Based on the observations above, Bootstrap seems as an ideal choice, since it beats Tailwind in most of the highlighted aspects.

\section{Documentation versioning}

As previously mentioned in Requirement~\ref{req:versioning}, the generator should support creating different versions of the documentation.
The section~\ref{sec:doc-versions} states that this should be achieved by creating a separate folder with documentation for each version.

As described in Requirement~\ref{req:doc-version-dropdown}, there should be a dropdown menu in the UI.
This brings us to two problems.
First, we need to ensure that the newly generated documentation version dropdowns include all of the older versions of the page.
Secondly, the older versions of the documentation must be updated to include the newest one.

In order to obtain all versions of the page, we can simply check whether the corresponding file exists in the version directories, but there is a more lightweight approach -- to store this information in a configuration file.
For instance, there could be an entry for each version containing its identifier and a list of pages generated.
This makes it easy to recognize all the older versions of a file.

The remaining problem is how to update the older version files to allow switching to the newest version.
The first option is to store the data in an external file (e.g., JSON) and fetch it on the client side using JavaScript. 
Then, when the page is loaded, the data is fetched.
Theoretically, this works well, however, there is a fundamental problem -- CORS. 
The problem is CORS, as several browsers, notably Chrome, 
When the documentation is hosted on a website, this may not be a problem, however, when created locally, the browser block access to cross origin files (and different file is a cross-origin request).
This is a major disadvantage.

An alternative way is to store the information in the HTML of each page (as a hidden element). 
This requires parsing all of the older pages when creating a new documentation version and assigning it to the list of available versions.
This approach may seem heavyweight, as it requires parsing a lot of pages, however, it is important to notice that the generator also does other potentially time-consuming operations, such as reflection or template processing.
Additionally, performance is often not a critical feature of the reference doc generators.
Furthermore, if this becomes a bottleneck in the future, this piece of code can easily be parallelized.
